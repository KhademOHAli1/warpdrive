# Better Auth migration: task list for approval

Status: **Approved by the user before implementation.** The original task list below is retained
for scope traceability. Current evidence and deployment limits are recorded in
[the implementation report](auth-implementation-report.md).

Prepared: 31 October 2026. Planning source baseline: Warpdrive commit `d496d15`.

## Outcome and scope

Replace custom human authentication with Better Auth and deliver complete sign-in, enrollment, account-security and administrator workflows. Preserve the current UI, existing user UUIDs, CRM record ownership, permissions, teams, visibility groups, regional preferences and authored content. Continue running the application on Bun with PostgreSQL and Drizzle.

This plan covers authentication and user administration for the current single-tenant, self-hosted open source distribution. Google Calendar implementation remains deferred. Mailbox and calendar connection consent remain separate from application login. Existing MCP client authorization must remain functional and obey account revocation.

Approval of this document approves the scope and proposed defaults below. Code, dependency installation, migrations and implementation experiments start only after approval. Production cutover follows a tested migration and recovery runbook; this plan does not authorize sending invitations to real users, connecting production providers or changing production access during development.

## Proposed defaults included in the approval

- **Admission:** invitation-only. A matching Google Workspace domain alone does not authorize joining. Public registration is closed across UI, callbacks and direct endpoints.
- **Login methods:** verified email/password and passkeys; retain Google sign-in, add Microsoft Entra ID and deployment-configured OIDC. Administrators choose which methods the installation allows. Enterprise self-service SAML/SCIM is a separate future scope.
- **Strong authentication:** mandatory for administrators, configurable for all users. A verified passkey with required user verification may satisfy the policy; other methods require the configured second factor. Social/OIDC sign-in must satisfy the same policy. No session awaiting enrollment or a second factor can access CRM data or issue credentials.
- **Recovery:** single-use recovery codes and a documented, audited operator-assisted lost-factor process. Recovery must establish account ownership; an email reset alone must not remove required MFA.
- **Accounts:** explicitly authenticated linking, verified recipient checks and collision handling. Do not automatically merge accounts using an email match. Do not permit removal of the last usable login/recovery method.
- **Authority:** Warpdrive keeps its existing authorization model. Better Auth administrator roles cannot create a second route around CRM permissions. Do not add the Organization plugin merely to implement invitations; CRM customer organizations are not authentication workspaces.
- **Sessions:** retain server-side revocation, hashed bearer-token storage, secure cookies and active-user checks. Define absolute/idle timeouts and fresh-authentication windows in the policy task. Do not adopt a default that weakens an existing protection.
- **Administration:** account deactivation, reactivation, ownership transfer, invitation and session management are included. Support impersonation and destructive user deletion are disabled in this initial scope. Provide an account-closure request and explain retention; actual deletion requires an explicit retention/ownership policy.
- **Languages:** complete Farsi workflows first, then German and English. Include transactional messages, errors, accessibility labels and operator instructions, not only page headings.

## UI workflow completeness checklist

Each surface includes initial, loading, validation-error, rate-limited, network/server-failure, success and cancellation states where applicable. Forms preserve appropriate drafts and focus; sensitive fields are cleared deliberately.

- **Public/auth:** sign-in, invitation landing/acceptance, invalid/expired/revoked invitation, email verification/resend, password setup/reset, provider redirect/error, passkey prompt/error, MFA enrollment/challenge, recovery, session expired, access denied and suspended account.
- **Personal:** profile, verified email change, linked providers, password change, passkey list/add/rename/remove, authenticator enrollment/remove, recovery-code acknowledgment/regeneration, device/session list and individual/all-device logout.
- **Administration:** user directory/detail, pending invitation management, delivery status, roles/permissions/team/visibility controls, suspension/reactivation, ownership transfer, session/grant revocation, assisted recovery, authentication policy and security audit trail.
- **Messages:** invitations, verification, password reset and changes to email, factors, providers, recovery or suspicious/revoked sessions. Avoid account-existence disclosure in public responses.

## Important upstream details to resolve deliberately

Better Auth documents a session table containing the session token. Warpdrive currently hashes bearer tokens before storage, so compatibility is an explicit qualification gate, not an assumed default. [Better Auth sessions](https://better-auth.com/docs/concepts/session-management).

The 2FA plugin does not challenge OAuth/social/passkey and similar passwordless methods by default. Enabling passwordless enrollment alone does not change this. BA-09 must enforce the approved assurance policy on every enabled path. [Better Auth 2FA](https://better-auth.com/docs/plugins/2fa).

The Admin plugin exposes role changes, bans, impersonation and deletion. Enable only the approved capabilities and enforce CRM authority at their server boundary. The Organization plugin introduces a separate workspace/owner model; adopting it needs a deliberate model decision. [Admin plugin](https://better-auth.com/docs/plugins/admin), [Organization plugin](https://better-auth.com/docs/plugins/organization).

Built-in rate limiting does not cover server-side `auth.api` calls and uses process memory by default. Shared storage and coverage of application-owned server actions are acceptance requirements. [Rate limits](https://better-auth.com/docs/concepts/rate-limit).

Other implementation references: [Next.js integration](https://better-auth.com/docs/integrations/next), [Drizzle adapter](https://better-auth.com/docs/adapters/drizzle), [passkeys](https://better-auth.com/docs/plugins/passkey), [generic OIDC](https://better-auth.com/docs/plugins/generic-oauth).
