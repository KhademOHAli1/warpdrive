# Privacy and data-lifecycle acceptance test design

Status: DESIGNED, not executed or implemented by this document. Traceability: [36-task backlog](privacy-data-lifecycle-tasks.md) and [PRD](PRD-warpdrive-privacy-data-lifecycle.md). The implementation chat must turn this design into executable tests and evidence before accepting tasks.

Current executable coverage and observed results are recorded in the [implementation register](privacy-implementation-status.md). The initial DESIGNED matrix is the acceptance contract; a passing subset does not qualify every scenario or a complete task.

## Test-first execution contract

For each behavior: write the failing test, run it and record the relevant failure, implement the minimum behavior, then rerun and refactor. Qualification tests of already-existing behavior may pass initially; label those as baseline verification rather than claiming a newly implemented feature. A test that merely repeats implementation values is not adequate acceptance evidence.

Use Vitest and disposable PostgreSQL databases with actual migrations. Use real local SMTP and S3-compatible storage when transport/object behavior matters. Fakes may exercise documented external-provider responses but do not establish a deployed provider's behavior. Never test erasure against actual customer data.

Candidate test locations below are proposed feature-owned files, not claims that files already exist. Expand case pairs into parameterized tests and the applicable cross-cutting matrix. Task acceptance requires all of its outcomes, including failure cases that need more than these minimum examples.

## Cross-cutting requirements

| ID  | Given / when                                                                                  | Accepted result                                                                                                                                                                    |
| --- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C01 | Substitute another actor, subject, case, record or artifact ID through any server entry point | No unauthorized read/write/disclosure and no existence leak; permission plus case scope enforced independently of hidden UI controls.                                              |
| C02 | Fresh authentication is absent/expired or MFA/verification is pending                         | Sensitive review, approval, execution and delivery deny safely; an existing factor or administrative protection is not bypassed.                                                   |
| C03 | Authority, policy, subject scope or approval changes after enqueue/start                      | Worker publication, destructive effects and retrieval recheck current generation/authority; no stale success or downloadable result.                                               |
| C04 | Cross-origin/cross-site mutation, missing/invalid CSRF proof or untrusted callback            | Request is rejected before effects under the applicable HTTP contract; signed provider callbacks retain their separately validated protocol behavior.                              |
| C05 | Repeat an operation, run two workers or crash at a commit boundary                            | At most one logical effect and one valid transition/receipt; safe retries repair incomplete work without fabricating success.                                                      |
| C06 | Abort, lose a lease, lose a provider connection or hit a timeout                              | Bounded termination and released resources; actual effects reconciled; partial outcome remains explicit and cannot be blindly repeated.                                            |
| C07 | Run every UI state, notification and date example in FA/DE/EN                                 | Natural complete copy; correct RTL/LTR, field direction, selected calendar/digits/time zone and invariant canonical IDs/deadlines.                                                 |
| C08 | Process the declared scale fixture or exceed a quota                                          | At most 100-record pages, streamed objects, bounded retries/memory, cancellation within the accepted profile and a usable truthful quota/error state.                              |
| C09 | Use only keyboard, screen-reader semantics, zoom and reduced motion                           | Labeled controls, logical navigation, focus containment/restoration, visible focus and live progress; critical content/actions remain usable at 320/390 pixels and in both themes. |
| C10 | Put secret/PII sentinels into hostile filenames, values, URLs and failures                    | No raw credentials, bearer links or prohibited subject content in logs, telemetry, referrers or routine audits; XSS, CSV formulas and archive-path attacks do not execute/escape.  |
| C11 | Introduce a real database/object constraint failure, upgrade or process restart               | Transactions, outbox receipts, foreign keys and resumable state stay consistent; no destructive reset of unrelated data or invalid migration shortcut.                             |
| C12 | A record concerns several people or contains an ambiguous match                               | Review/provenance and third-party disclosure rules apply; no automatic merge, ownership-based full export or deletion of another person's data.                                    |
| C13 | Refuse/clarify/extend a request, send a draft response or lack operator facts                 | Reasons, receipt/deadline and human decision are retained; no invented notice/controller facts or automatic external communication.                                                |
| C14 | A hold, approved exception, shared reference or provider restriction applies                  | The applicable hold wins at execution; retained/blocked/external residuals are listed and never counted as verified erasure.                                                       |
| C15 | Restore a snapshot older than deletion/revocation decisions                                   | Admission/jobs remain blocked until current integrity-checked lifecycle records are replayed and verified; erased data and old access do not reappear.                             |
| C16 | Expire/revoke an artifact or interrupt a legitimate range/retry transfer                      | Unauthorized retrieval fails promptly, authorized retry semantics remain bounded, and storage/metadata cleanup has a durable verifiable outcome.                                   |

## Evidence and closure record

For every test family, retain command/configuration, exact commit/tree, runtime versions, fixture IDs, assertions/results, resource/failure measurements and any manual review. Redact secrets and unnecessary personal identifiers from captures. Store screenshots of the actual FA/DE interfaces where visual acceptance is required.

Machine-check task IDs, test IDs and dependencies for completeness and cycles. Acceptance is not satisfied by writing this matrix, by reporting a percentage without its denominator, or by substituting a fake transport/device for a required installation check. Keep a clear list of OPEN external gates and do not mark the full implementation goal complete while a required gate remains unresolved.
