# Newsletter engine final-image qualification

The independent `production-engine.yml` workflow builds the unchanged, digest-pinned engine recipe for Linux/amd64. It adds revision and exact-context labels without replacing upstream source attribution. It has read-only repository permission and no registry publication, provider or production deployment credentials. Its [Docker container builder](https://docs.docker.com/build/builders/drivers/docker-container/) uses two CPUs and a 2 GiB memory/swap ceiling. Local tooling checks are not a successful hosted final-image run.

The harness accepts an already-built image:

```sh
python3 -B scripts/deployment/engine_image_smoke.py \
  --image warpdrive-engine-ci:example --expected-revision FULL_GIT_SHA \
  --old-image warpdrive-engine-old-ci:example --old-context /path/to/verified-old-context \
  --output-dir /path/to/new-evidence-directory
```

It admits only a local Unix Docker endpoint on a native host with a visible Docker data root. It uses an isolated Docker auth configuration and generated synthetic credentials. The inspected immutable image ID is used for every engine container. Containers run on one owned internal network, publish no ports, drop capabilities and use bounded CPU/memory/PIDs/logs. Engine processes use the image's declared UID/GID 65532, a read-only root, and small writable tmpfs mounts for uploads and temporary files. The only host bind is an owned, generated, read-only synthetic password file; there are no runtime source mounts. PostgreSQL uses an owned disposable volume. Providers and delivery are disabled.

The `_FILE` probe deliberately requires the generated database password in plaintext: the unchanged final-image entrypoint reads a regular file and must authenticate successfully while the direct environment value is deliberately wrong. Native-host admission now precedes provisioning. The harness requires `/dev/shm` to be an actual writable `tmpfs` in the host mount table, matching its filesystem device; it refuses unavailable, ambiguous, symbolic, read-only or disk-backed storage without a fallback. Every ancestor remains open through nofollow directory descriptors. The owned mode0700 parent must retain its admitted identity; a literal leaf is created exclusively relative to its held descriptor. Owned, single-link mode0600 file and name identities are checked before the visible plaintext write. The file becomes mode0444 only after flush for the image's UID65532 to read its read-only bind mount, with authority checked again after wrapper close. The parent remains private; normal failure/signal cleanup removes the file after owned containers are removed. The payload is outside retained artifact paths, and diagnostics redact generated credentials.

The source-bound review and caller-expiry guard remain in `docs/deployment-evidence/fixture-codeql-exception-20261112.json` for historical continuity. Its current schema records intentional plaintext without a scanner annotation. The prior annotation did not clear managed alert23 and was removed; exact changed-source analysis and named-ref finding disposition remain required. Creation hardening does not eliminate the later Docker pathname-bind race or make an identity-check followed by unlink atomic against the same UID/root. These remain trusted-host residuals in the independent review.

This reduces default temporary-file persistence; it does not assert secure erasure or unswappable memory. `tmpfs` can use swap, and the same synthetic credential exists in PostgreSQL Docker configuration, CLI arguments and process environments. Other host UIDs may observe those CLI arguments on a normal Linux process table, so private file provisioning is not a claim of credential secrecy from every host user. Host root, the runner UID and the admitted local Docker daemon remain trusted. These are disposable generated credentials for an internal fixture, with no production credential input or provider access. CodeQL's [`py/clear-text-storage-sensitive-data` rule](https://codeql.github.com/codeql-query-help/python/py-clear-text-storage-sensitive-data/) correctly identifies the literal plaintext file write; its [owning sink model](https://github.com/github/codeql/blob/main/python/ql/lib/semmle/python/security/dataflow/CleartextStorageCustomizations.qll) does not distinguish private tmpfs from persistent file storage. Storage hardening alone is not evidence that the exact-revision CodeQL alert has cleared.

Packaging checks run the default entrypoint and verify actual nonroot execution and image-owned uploads ownership. They bind the copied amd64 ELF executable, installed entrypoint and corresponding-source archive to the exact reviewed context and pinned upstream source. Reapplying the archived patches and reconstructing the build recipe's installer hash checks that the binary embeds that hash. This is not a reproducible-build proof. The source archive intentionally contains corresponding source required by the engine license; unpacked application/build sources and environment files are rejected in the final runtime layout.

The existing native migration probe functions operate through Docker adapters, executing each migration/runtime command in the actual final image. They cover empty-database runtime refusal; authenticated file-secret loading and missing/unreadable-file rejection; fresh and repeat migration; pinned-schema legacy holds; receipt/schema/RLS/policy/sequence drift rejection; a restricted database role with a DDL-denial event trigger; actual shared/exclusive lock contention; fence-session loss; and passive health/readiness. The restricted role's synthetic TCP password is arranged by the fixture owner before startup. HTTP probes run inside the owned container; no host listener is needed. All fifteen original checks remain, including the pinned-schema case.

An additional supported-old packed-binary rehearsal builds commit `35c40339b8068a489247080e61430d17bfbfdb26` using its unchanged historical recipe. A depth-one sparse checkout is verified against the exact Git commit object, engine tree `72c4eb357e6981315909fb134c021f1c5eaa2025`, every original blob and a fixed39-file SHA-256 manifest. Only those verified files are materialized under `RUNNER_TEMP`; the temporary checkout is removed. Old and new images build sequentially on the same bounded builder. The old OCI revision stays `35c40339...`, and both inspected immutable image IDs, artifact hashes and original source contexts are retained. The old image's root-default identity is reported honestly and admitted only for its owned historical fixture; the candidate still must default to UID/GID65532.

The supported-old path passed all sixteen checks in [native Linux run 43148013207](https://github.com/KhademOHAli1/warpdrive/actions/runs/43148013207), at source `f8248dbb58370b09cbedf8803c67342160cb166c` and tested merge `0142144b21971d6a87a98fefd76fc793e0075959`. `docs/deployment-evidence/engine-linux-f824-20261112.json` binds the API-digest-verified artifact, report, image IDs, original contexts, exact media bytes and successful cleanup. This qualifies the stated synthetic baseline upgrade, not an installed VPS or another source revision. Earlier fifteen-phase results alone do not establish this added check.

The old packed binary installs a distinct fresh PostgreSQL cluster and writes media through its real authenticated media API. A cursor-bearing campaign is inserted between old installation and first passive startup, so the actual old v1 migration must establish its legacy hold. Synthetic verified/revoked consent rows, a keyed suppression tombstone, pending/unknown/rejected delivery receipts and pending/acknowledged operational events exercise preservation. These SQL fixtures do not assert that a real person consented or that a provider accepted mail. The old process is stopped; container PID/state, remaining old-image containers and old database sessions are independently checked before cutover. Any unknown stop result holds migration. The old binary cannot be launched after that fence or against the migrated schema.

The binary multipart request is streamed through `docker exec --interactive` to the old container's fixed loopback HTTP endpoint using its existing BusyBox `nc`. Credentials and PNG bytes stay on bounded stdin. This avoids both the read-only-root archive/copy limitation and BusyBox `wget --post-file`'s C-string truncation of binary data. A fixed pipeline caps response bytes before host buffering; strict bounded Content-Length/chunked framing, HTTP200, safe filename and exact uploaded PNG bytes are all required. The report retains only finite API/byte-verification phases and numeric status, without payloads or authentication headers. The root remains read-only; no image recipe or extra package changes are needed. The retained native run observed HTTP200 and preserved the exact 69-byte PNG through the supported-old upgrade.

Only this newly owned media volume undergoes a bounded, explicit offline ownership handoff of its enumerated paths. Existing production-volume migration is not inferred. The new explicit migrator must preserve existing table-row fingerprints and create its receipt; repeating it must change no table/catalog/sequence state. New restricted-role/no-DDL admission and passive startup must preserve consent, suppression key, receipt identities/ACK states, pending/unknown writer holds, legacy campaign/cursor and exact API-uploaded media bytes. The supported-old case is a synthetic, reviewed source baseline, not an observed VPS installation upgrade or general compatibility claim.

Runtime qualification has a fifteen-minute deadline, 3 GiB observed host-disk growth budget and 8 GiB reserve. Resource pressure or missing checks fails the result. Cleanup verifies ownership before removing all current/historical containers, owned media/database volumes and network; cleanup failure prevents success. Failed-first logs are bounded and redact generated secrets. The report records executed checks, immutable IDs, context/input hashes, copied artifact hashes and limitations. A successful non-PR run retains that same tested candidate image by ID without rebuilding or publishing it.

Existing upload-volume ownership changes, an actual installed-version/VPS upgrade, independently verified installed offline migration control, unknown-outcome writer holds, provider/SMTP delivery, restore, ingress and production acceptance remain separate gates. The cooperative advisory fence does not replace verified process stop before supported schema maintenance.
