# Reviewer intake interface

The privacy settings root now offers a separate reviewer intake card after the existing personal-request form. Requester case-detail pages remain requester-bound and do not mount this queue. The UI uses the existing settings surfaces, buttons, locale direction and date/time formatters. Farsi, German and English copy is complete; UUID references remain LTR inside RTL text.

The initial card does not fetch requests. An explicit load first rechecks the current native security status, then invokes the existing reviewer Server Action. Neither administrator status nor a client reviewer UUID supplies authority. The UUID only rejects a stale form. The server requires current `case.assign` for the minimal intake view; initial assignment also requires `authority.manage` and `case.review` in the existing transaction service.

The live view displays only the opaque case reference, type, status, received instant and response due instant. Each request is bounded to 25 rows. Load-more uses the exact returned cursor and deduplicates repeated IDs to the latest returned version. It does not establish a stable snapshot, complete subject scope or permission to read case contents. No reviewer link reuses the own-request detail route. The separate exact-case entry described below also remains outside that requester route.

Taking a case freezes its case ID, current version and one command ID. An unclear response retains that intent; explicit retry uses the same command after another security check. No mutation is automatically resent. A recorded receipt is historical and does not assert current ownership, disclosure approval, data changes or case completion. Refreshing obtains a new live view rather than deriving current state from the receipt.

Account changes, sign-out, MFA/enrollment requirements and unavailable security status hide cached reviewer data and suppress late results. Current access/freshness denial also clears a previously recorded receipt. The same-account uncertain command remains available for safe reconciliation after access is restored. Personal-form state is separate; shared security-check supersession cannot authorize a retry from a stale result.

All reviewer content is inside the existing replay-block/no-capture boundary. This is a source declaration, not installed telemetry acceptance. Intents live in component memory, not a durable browser store. Closing or reloading the page does not establish a remote rollback or a verified memory erase. Existing database idempotency and version checks remain the mutation authority.

## Preserved reviewer source completion, 10 November 2026

The privacy root now mounts a separate exact-case reference entry after personal intake and reviewer triage. It starts with an empty reference and performs no automatic case lookup. A selected UUID mounts two independent explicit reads: original request context, and a preliminary native subject projection. Changing the reference or current security boundary removes the previous selection and its displayed data. Requester case-detail routes do not mount reviewer components.

`readPrivacyReviewerCase` replaces the local denial scaffold. It accepts only a case UUID and uses current fresh native session checks plus global and assigned membership `case.review` authority. Case-row locking is followed by another current-session check before decoding authenticated original intake. The response contains only the bounded original subject/recipient/summary/locale/kind and minimal case/policy/identity state. Original intake is never replaced by current verification evidence, and the original intake idempotency key, raw actor/session references, encrypted evidence and policy contents stay private. Invalid ciphertext/schema and non-finite dates return static `evidence_unavailable`.

The native subject read requires current `case.review` and `case.disclose`, an under-review access/portability case, a current verified identity and active disclosure-enabled policy. It reads only the exact native user or contact projection with source locks and bounded schema checks. Its contract remains `complete:false`, `reviewRequired:true`: it neither approves a durable disclosure scope nor discovers every related record.

The triage card can explicitly begin verification through the existing case-transition command. Uncertain commands retain the same UUID and expected version for deliberate reconciliation; a recorded transition is historical. The bounded discovery-status connection factory remains an internal service building block with no new HTTP endpoint or background polling caller.
