## Concrete driver and proposed operation

The actual driver is node-postgres `pg`. `Db` is the base `NodePgDatabase<typeof schema>` from `src/db/client.ts`, usable by both the production handle and actual `makeTestDb()` fixture. The real transaction callback type is extracted as already done by native source, rather than substituting a root Db for a transaction. The public `TransactionRollbackError`/`tx.rollback()` behavior is used by `nativeAuthGateway`; error-valued Result alone does not roll back a transaction.

Proposed feature-local API: `runAuthorityTransactionCandidate(db, spec, signal, operation)` returns Promise<Result<T, E | authority_transaction_unavailable | authority_commit_outcome_unknown>>. It is a review candidate, not the absent accepted Platform/shared authority API. `operation` receives the actual transaction and required AbortSignal and returns an actual Result. No project permission, identity, scope or Privacy admission is inferred.

`parseAuthorityTransactionSpec(unknown)` validates native candidate configuration exactly once: strict required key tuple of two signed int32 values, fixed shared/exclusive mode and lock/statement/idle timeout milliseconds. Each timeout is an integer1..60000 and lock<=statement<=idle. Valid syntax reserves no production key or budgets. Tests use explicit synthetic keys only. No default key, string-hash namespace, browser authority DTO or production key assignment is introduced.

The planned outer transaction requests READ COMMITTED, configures transaction-local SQL timeouts using constant setting names, then obtains one transaction-level `pg_advisory_xact_lock_shared` or `pg_advisory_xact_lock` with the supplied key. Authority/business reads are separate statements after that awaited lock. No helper lock upgrade or nested transaction is introduced. Ordinary PgTransaction/savepoint arguments must be rejected using the actual public runtime type; a plain Db type alone does not prove ownership of the outermost backend transaction.

An error Result is captured outside the callback and invokes `tx.rollback()`. The rollback exception is handled only outside the outer transaction. An unexpected database error after an OK callback has entered COMMIT must retain an unknown-commit outcome, not become evidence of an unsaved operation. AbortError must propagate; tested pre-commit cancellation is distinct from the unqualified COMMIT-cancellation case.
