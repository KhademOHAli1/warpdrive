## Current-native authority and create contract

Use actual `createContext`, `protectedProcedure`, `guardCsrf`, `requireFreshIdentityAction`, `hydrateActor`, `toRefActor` and `assertReferenceVisible`. None is a project grant by itself. Do not borrow `deal.create`, `workflow.view`, a permission-set display name, an assignee exception or a client-provided boolean to authorize this new domain.

Proposed narrow global addition: `project.create`, default denied for ordinary permission sets. Add it to the actual permission registry and FA/DE/EN labels through a reviewed patch. Its create check, native administrator behavior, high-risk classification and grantor rules require explicit acceptance. The separate project-private membership policy also needs acceptance; it must not accidentally rewrite native parent visibility or the shared administrator contract. The global create flag authorizes creation only, not existing project access or financial data.

Project owner or persisted membership supplies project read/edit/assignment grants. A member row means read; edit and coordinate are independent persisted grants. A coordinator need not edit project customer links/title; an editor need not coordinate assignments. An editor cannot change membership or owner merely because it can edit the project. No financial permission or field is introduced by this core delta. Global flag and local-grant semantics remain proposed until the named owners accept them.

Create input contains a stable intent UUID, bounded title, explicit accepted internal owner and canonical CRM links. The selected owner must be active and have completed invitation acceptance. Recommended creation behavior is to record the creating actor as an explicit read member with project-edit grant when it differs from the selected owner. Its assignment-coordinate grant remains false unless a separate authorized owner command grants it. This concrete default avoids coupling edit and coordination; it remains subject to the same owner review as the action table. Validate creator and selected owner's applicable CRM ceilings rather than granting CRM access by assignment.

Two actual API gaps require explicit checks: `assertReferenceVisible` does not reject `deals.archivedAt`, and its user-reference check does not reject a nonnull `users.invitedAt`. Enforce those selected-deal and accepted-staff rules in project commands. Recheck pipeline archive, deleted parents, actor status, permission-set assignment/flags and project membership inside the transaction before commit. `hydrateActor` is a refresh, not authentication or an authority lock. Existing auth-account/MCP locks do not establish a general permission-writer fence.

## Atomic operations and reads

Create, request receipt, initial history and permitted membership commit in one transaction. Under the new protected-content proposal below, any required reason payload also commits in that transaction. Compare the same intent's canonical input before returning an existing receipt. A new intentional project uses a new intent. Never mutate won/lost acquisition state or use deal stage as production state. SP-09 automatic handover remains unavailable until its real owner API exists; explicit authorized CRM linking can be tested independently.

Transitions load current authority and state, invoke the existing pure policy, then update with `WHERE id AND revision = expectedRevision`. Exactly one concurrent writer wins. Insert its minimal history, any required protected reason payload and request receipt only in that successful transaction. No activity, notification, workflow or outbound effect follows from core create/cancel/archive. A queue being unavailable therefore cannot be reported as an unsaved core write.

Get/list/count/export/search/realtime/MCP must use one project scope: current project owner/member access intersected with every authoritative CRM parent ceiling. Hidden, deleted or unavailable parents must not fall back to a broader organization or parentless rule. Lists filter before paging/counting; a shared saved view grants no records. First list uses a declared cap and stable cursor with minimal DTOs. New export/realtime/MCP surfaces stay unregistered until their scoped paths exist and pass denial tests.

### Recommended fifth store, not yet owner-reviewed or allocated

Recommend an optional one-to-one protected-content record per history event rather than permanently immutable plaintext reasons in `agency_project_history`. A reason-required transition creates both records atomically. An event whose policy permits no reason has no protected payload; absence must not be confused with a reason later redacted or expired. Proposed names and fields below are review input only.

Even minimal actor/reference facts remain protected personal data with an explicit purpose. | Privacy must decide permitted retention/redaction exceptions for identifiers. | NEW `agency_project_history_content` | `history_id` as the unique history-event identity, with same-project linkage; payload contract version; protected bounded reason ciphertext when present; encryption/key-version reference; explicit present/redacted/expired disposition; and minimal authorized disposition provenance. A later redaction clears the protected payload while retaining an explicit disposition where policy permits, rather than rewriting the original event as though no reason was supplied. | This fifth physical store, its FK/uniqueness rules, encryption/key lifecycle, permitted disposition writer, retention/holds and indexes need Privacy and allocator review before any allocation or DDL. No adopted encryption/key API, redact/erase endpoint or lifecycle grant is implied. |

Read/decrypt joins use the same current project/CRM ceiling plus the accepted content-disclosure rule. A dedicated authorized history-content projection may display a permitted reason; list/summary DTOs, persisted idempotency receipts, routine audit events, errors, logs and realtime summaries do not copy it. The pure server-only policy receipt may carry the validated reason to its future atomic writer; it must not be spread into those public or diagnostic surfaces. An ordinary editor cannot replace or redact old reasons through a project update. Any future authorized lifecycle change must preserve a minimal disposition receipt without duplicating the removed content. No redaction, expiry, retention period, hold release or deletion runs by default, and none is implemented by this amendment.

Encryption is an additional proposed protection, not proof of erasure. Key separation must permit the approved disposition for one payload without destroying a key shared with unrelated live records. Exact key storage, backup residuals, restore behavior and supported crypto operations require actual owner-reviewed interfaces and evidence. Do not introduce a fictional broker or declare ciphertext erased merely because one reference is removed.

The four-store alternative is to keep a separately protected payload column with narrowly scoped immutable-fact guards in the same history table. The recommended fifth-store separation makes the two writer responsibilities explicit, but it is a NEW design choice. ### Private request fingerprints and non-replayable tombstones

The historical raw SHA-256 column is not a settled privacy design. Specify a canonical serialization contract/version and actor/operation/intent domain binding, preserving semantic input distinctions and excluding transport noise.
