## Selected ordering contract

Use one stable fence identity for the application database, shared by native HTTP, workers and host/operator paths. Actor- or project-specific keys are insufficient for workspace-wide policy, permission-set and team changes. Platform must own the collision review, exact key and transaction API; this review allocates neither a SQL key nor a new export. Use transaction-level locks, not pooled session-level locks. PostgreSQL advisory locks require application participation and transaction-level locks release at transaction end. [PostgreSQL locking](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS)

| Mode | Eligible operations |
| --- | --- |
| Shared | A project command whose exact write set cannot change authority/admission for another command. A title-only update can qualify if it does not re-emit owner, membership, CRM links or admission state. Project revision CAS remains required. Pure scoped reads may use this mode where their disclosure contract requires it. |
| Exclusive | Every mutation of any input to the accepted authority/admission predicate: user/native role/permission assignment, flags, session/factor/policy, team/group membership, parent visibility/availability/relationships, project owner/member/grants/authoritative links, and lifecycle/Privacy changes that alter admission. Unclassified project mutations begin exclusive. |

Do not classify all project mutations as shared. Owner/member revocation, relinking and admission-changing archive/cancel paths must be exclusive from entry. No shared-to-exclusive upgrade is permitted; abort and restart the whole transaction under the correct mode if the planned operation changes. Retain existing domain CAS, row constraints, idempotency and Privacy checks: the fence is ordering, not an authorization grant.

For each participating command:

1. Validate syntax, CSRF/origin and coarse availability without trusting cached actor/parent data. Any preflight identity or dependency lookup is only a hint.
2. Start the outermost database transaction with explicit `READ COMMITTED` and finite database wait/statement bounds. Acquire the fence before touching authority rows or taking account, MCP, lifecycle, import, project or recovery-case locks.
3. After fence acquisition, issue separate statements to resolve current native session/authority and all canonical project/CRM/owner/Privacy predicates. Do not combine the blocking advisory-lock call and authority reads in one statement, or reuse a snapshot established before waiting. Under Read Committed, each command starts with a fresh snapshot. [PostgreSQL isolation](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-READ-COMMITTED)
4. Take required existing domain locks in a documented consistent order, using sorted IDs for multi-account/row sets. Preserve account-before-MCP-before-user ordering where those locks coexist. Each path that combines lifecycle/import locks must have one reviewed order. Pass the same transaction and already-selected fence mode through nested services/savepoints. A low-level helper cannot start an independent pool transaction or acquire the outer fence after earlier locks.
5. Recheck any mutable business dependency after waiting for its lock. Apply revision/intent checks, then commit the project, history, protected content and request receipt atomically. If a failure occurs after a project write, abort the transaction; returning an error-valued `Result` from a successful transaction callback does not itself roll back writes. Never emit a success audit/history/receipt for an aborted project mutation.
6. Keep the fence through commit/rollback. Retry only a whole transaction with fresh checks and the same logical intent. An unknown commit result requires receipt/status reconciliation before offering duplicate creation.

This gives a precise ordering for participating database mutations: if a project holds shared access first, revocation cannot commit until that project transaction finishes; if revocation commits first, the project's post-fence reads must see it and deny where applicable. Revocation request arrival is not its commit point. A fence does not freeze clock-based expiry/freshness; re-evaluate native time predicates after waits and immediately before the final write. Any stricter expiry-at-commit requirement needs its own explicit platform contract.

## Required corrections to the source plan

**Final native verification must be read-only.** `resolveWorkflowSession()` currently evaluates `lastSeenAt` and can then update it (`src/features/auth/better/sessionPolicy.ts:48`, `:81`). There is no no-touch option. The update samples time before I/O and writes by session ID, so monotonicity is not established; legacy `src/features/auth/session.ts:93` has the same pattern. Native-auth should add an explicit no-touch final-verification option/path that reuses the existing resolver/evaluator. Do not duplicate authentication logic or upgrade a shared fence inside that resolver. Usual touches need an exclusive bounded boundary, or a separately reviewed and proved monotonic-maintenance exception. Current source supplies neither exception.

**The outer transaction owns the fence.** `reviewRecoveryRequest()` locks a case before calling `setUserActive(tx)` (`src/features/auth/management/administration.ts:79`, `:90`). Import/merge acquire `import_mutation` before nested repository operations. Enrichment locks a contact before calling its repository. Adding the fence only to those inner services would introduce earlier-lock-to-fence inversions and retain stale pre-fence decisions. Update the encompassing entrypoint and inherit its transaction.

**Nominal content updates can rewrite authority fields.** `updatePerson()` re-emits resolved organization and owner (`src/features/contacts/personsRepo.ts:161`, `:191`); `updateOrg()` re-emits owner (`src/features/contacts/orgsRepo.ts:158`, `:165`). Fence the whole enclosing writer, including enrichment/import reuse, unless a separate reviewed refactor proves those fields are never re-emitted. Checking only raw input for `ownerId` misses this case.

**Bound actual SQL, not just JavaScript waiting.** Existing account/MCP helpers only check an `AbortSignal` before and after awaited SQL; `src/db/client.ts` configures no database timeout. Recommended pilot budgets are at most 2 seconds per lock acquisition, 5 seconds per statement/idle-in-transaction interval, and a 10-second whole-command cancellation budget, with no automatic HTTP retry loop. These are proposed qualification inputs, not measured service levels. Use transaction-local settings and verified driver cancellation/rollback/connection disposal for the total budget. A rejected promise alone does not prove the backend released its locks. The source deployment and integration fixtures use PostgreSQL 16 (`docker-compose.yml:40`, `vitest.globalSetup.ts:45`); do not prescribe the newer `transaction_timeout` setting for that lane. Lock and statement timeouts have separate meanings and neither is a whole-transaction timer. [PostgreSQL 16 timeout settings](https://www.postgresql.org/docs/16/runtime-config-client.html#GUC-LOCK-TIMEOUT)

Keep network/provider work and user interaction outside the fenced critical section. The current native gateway wraps a whole handler: simply adding a database-wide exclusive lock there is not proof of a short, bounded section. Native-auth must show a transaction-local adapter boundary that spans the mutation and its hooks without external waits, or supply another explicitly bounded design. Releasing and reacquiring the fence midway is not equivalent.

## Module admission selection

Select one central operator boolean, proposed name `AGENCY_PROJECTS_ENABLED`, using the existing strict parser and default false. Patch `src/config/env.ts`, its tests, `.env.example` and operator deployment documentation; add feature-local checks only when actual Agency server readers/commands/consumers exist. No generic module broker or provider/licence dependency is needed. Current Agency source has pure policy/schema/template modules, not persisted routes or worker consumers.

The initial disabled contract is **all Agency reads and commands unavailable**, including history, counts, request-status recovery and protected reasons. Preserve data in storage. Return the common bounded unavailable state, not a successful empty list; discard now-unavailable client projections. This matches `docs/agency-projects/workspace-state-spec.md:39`. A disabled-history exception requires a separate server disclosure policy.

Treat this env value as startup admission, not immediate revocation. Stop new admission, drain bounded admitted transactions/effects, stop/drain relevant consumers, then restart every relevant replica with the intended value. A transaction admitted before that drain may finish. Verify the same immutable application cut and switch value across app/worker/operator processes before reopening admission; old unfenced authority writers cannot coexist with enabled Agency persistence.

Future durable jobs must check availability at scheduling and actual consumption/effect admission. Preserve pending intents while disabled without acknowledging skipped work as success or consuming retry budgets solely because the module is off. Re-enable reconciles once with fresh authority. Do not add a queue to project-only core writes: the present draft intentionally has no required background effect for create/cancel/archive. Queue failure cannot make an already committed core mutation “unsaved.” A requirement for immediate cross-process disablement needs a separately reviewed runtime availability generation/fence; an env edit does not supply it.

1. Real PostgreSQL races in both orders: project holder first versus permission/status/native-session/policy/factor/team/group/project-member/parent/Privacy revoker first. Include absent-policy creation and new membership/passkey rows.
2. Native session/user inversion, recovery-case nesting, import/merge/enrichment outer-entry ordering, stale actor/relationship plans and final no-touch verification. Explicitly detect entrypoints that bypass or escape the fence transaction.
3. Cancellation, lock/statement/total timeout, deadlock, rollback and connection reuse/disposal. Assert no lingering backend lock and no successful project history/audit/receipt on rollback. Test unknown-commit receipt recovery.
4. Concurrent independent eligible shared project commands, revision conflicts, exclusive-writer contention and bounded progress of unrelated work. The global fence's contention cost must be measured before performance claims.
5. Module-off denial before Agency reads/writes, protected cache/history handling, drain and mixed-version/config behavior, durable queue preservation and idempotent re-enable. No future external effect is qualified by database fencing alone.
6. Separately accepted project action/membership policy, Privacy/store coverage, canonical migration lineage/allocation and fresh/upgrade/rerun/restore evidence. Narrow `project.create` registration acceptance settles none of these.
