## Proposed feature-local boundary and policy

These are proposed pure functions, not HTTP routes, shared service exports or authorization APIs:

- `parseReviewAction(unknown)`: strict browser-action boundary returning `Result<ReviewAction, "invalid_review_action">`.
- `parseReviewCommand(unknown)`: strict server-assembly boundary returning `Result<ReviewCommand, "invalid_review_command">`.
- `applyReviewCommand(ReviewSnapshot, ReviewCommand)`: pure decision returning `Result<{ snapshot: ReviewSnapshot; receipt: ReviewMutationReceipt }, ReviewFailure>` consistently for every admitted command.
- `currentReviewApprovals(ReviewSnapshot)`: server-only derived arrays `{ internal, recordedClient }`, each retaining individual current-version/current-epoch evidence. There is no universal approved or all-clients-approved flag.

The action/command parsers reuse actual `canonicalUuidSchema`, `revisionSchema`, `referenceSchema` and bounded `reasonSchema` from `valueSchemas`. They do not normalize external references. The pure policy consumes validated data once, following the existing assignment boundary/policy split. Input validation does not establish native identity, record authority or actual occurrence truth.

## Data and provenance

The proposed server-only snapshot contains canonical project and deliverable UUIDs, optimistic `revision`, a nonnegative `reviewEpoch`, server-owned `reviewOpenedAt` and `lastRecordedAt`, exact `currentVersionReference` and append-only decision history. The new `lastRecordedAt` field is a trusted high-water mark for every committed mutation, including reference-only changes, and initially equals the opening time. Browser actions and command bodies cannot supply either snapshot clock field. A snapshot exists only after an identified submitted version; there is no placeholder or pre-submission review snapshot. The epoch distinguishes an expressly reopened review of the same external version from its earlier approval. It is an internal invalidation marker, not an included/commercial revision-round count. A real persisted snapshot parser and coherent authorized loader are still required before storage or runtime use; TypeScript structure alone does not establish version ownership, temporal coherence or valid history. That loader must prove `lastRecordedAt` is at least the opening and every committed decision/mutation recording time, with exact instant comparisons and coherent version/epoch history.

Every public action identifies the project/deliverable and expected revision. Record actions carry the exact reviewed version reference, a bounded safe evidence reference, explicit method and actual reported `occurredAt`. These timestamps require valid ISO instants with an explicit numeric offset or `Z`; no language, calendar or timezone is inferred. Fractional seconds up to nine digits are supported, and the original timestamp strings, including supplied offset and fractional digits, are retained. More than nine fractional digits are rejected explicitly. A missing/unknown occurrence cannot silently become the recording time.

The server must add canonical native `recordedByUserId` and its actual `recordedAt` instant after native request policy passes; that service/auth assembly is not implemented here. The implemented browser-action boundary rejects these fields on every action variant. Server command parsing requires both and rejects malformed/offsetless recording timestamps on every command, including change/reopen. Record commands reject an occurrence after the supplied server recording instant at full supported nanosecond precision. For example, `06:00:00.000000001Z` is after `06:00:00Z` and fails, including its offset-equivalent representation. The installed `@js-temporal/polyfill` compares `Temporal.Instant` values without converting through `Date.parse`, floating-point milliseconds or another rounding step. Equal instants represented with different explicit offsets remain acceptable, while their source strings remain unchanged. These precise-ordering cases passed in the selected pure unit run. No wall clock is read by this module. Native recorder UUID and selected client-person UUID remain separately named and validated domains; their values do not authenticate an external party or establish subject identity.

The proposed decision variants are:

| Action | Stored kind and outcome | Additional provenance |
| --- | --- | --- |
| `record-internal-review` | `internal-review`, explicit `approved` | Method is `internal-review`; native recorder, exact version, evidence and occurrence/recording times. |
| `record-client-approval` | `staff-recorded-client-approval`, explicit `approved` | Selected canonical `clientContactId`; manual method `email`, `phone`, `meeting` or `message`; native staff recorder and evidence/times. |

Each history entry binds the current epoch and the next `recordedAtRevision`. History retains individual records for different client contacts. A staff-recorded client approval does not create an internal approval. Neither variant creates external authentication, a signature, provider verification or communication-delivery evidence. Unknown fields such as authenticated-client/signature flags and provider-verified method shortcuts are rejected. Actual client consent/approval evidence is a staff-recorded fact, with its declared source and limitations.

This small proposal records approvals only. Change-request conversion, rejection/disposition policy, commercial included rounds and assignment-state coordination remain separate work. It does not create a second task engine.

## Revision and version rules

The policy first compares expected revision. A mismatch returns `revision_conflict`, including replay and approve/change ordering. Matching revision but a different project or deliverable returns `review_target_mismatch`. A record action referring to a different exact version returns `review_version_conflict`. Reference comparison is byte-for-byte; it does not equate URL case, escaping, query order or other textual forms by fetching or canonicalizing them.

An admitted record increments the revision once and appends a new decision without changing previous history or the caller's snapshot. `change-version` takes a new exact safe `versionReference`, expected revision and bounded nonblank reason, plus server recorder/time. It increments revision and epoch while preserving old decisions. A textually unchanged reference returns `version_unchanged`, requiring explicit `reopen-review` instead. Reopen requires expected revision and nonblank reason and advances epoch while retaining the exact version reference and all prior decisions. Change/reopen reject missing, whitespace-only or oversized reasons and disallowed C0/C1 controls at both public-action and server-command boundaries. The existing bounded reason schema may perform its declared trim once; the policy must preserve the resulting validated reason exactly, including its remaining Persian/German text and permitted ordinary whitespace, without translation, replacement or further truncation.

Every admitted operation also returns a policy-versioned mutation receipt:

| Receipt fields | Required retained provenance |
| --- | --- |
| `policyVersion`, `action`, `projectId`, `deliverableId` | Policy version 1, the actual admitted command and canonical target scope. |
| `previousRevision`, `revision` | Exact old and new optimistic revision. |
| `previousReviewEpoch`, `reviewEpoch` | Exact old and new review epoch; record actions retain the epoch. |
| `previousReviewOpenedAt`, `reviewOpenedAt` | Exact old and new epoch opening strings; record actions retain the opening. |
| `previousRecordedAt`, `recordedAt` | Exact old high-water string and the trusted command's new recording string. |
| `previousVersionReference`, `versionReference` | Exact old and new external references, including identical references for reopen/record actions. |
| `recordedByUserId`, `recordedAt` | Native server recorder and its actual supplied recording time. |
| `reason` | Exact validated bounded reason for change/reopen; `null` for record actions. |

The receipt ensures reference-only change/reopen operations cannot discard who changed what, when and why merely because they append no approval decision. This is returned pure data only. A later actual transactional history writer must preserve approved reference/epoch transition receipts together with the snapshot mutation under the accepted ownership, schema and privacy contracts; no such writer or persisted transition history is claimed here.

The explicit edge tests require `revision_exhausted` before every command would increment an already maximum safe-integer revision. `change-version` and `reopen-review` return `review_epoch_exhausted` before incrementing an already maximum safe-integer epoch. Recording a decision at a maximum epoch remains possible when revision headroom exists because that operation does not consume an epoch. Failed operations preserve input history and return no success receipt. These overflow guards passed the selected unit run after their observed assertion red.

Current approvals are derived only from decisions matching both current version and epoch. Old decisions therefore survive new versions/reopening without approving new work. Separate arrays do not claim that every required reviewer/client approved; the relevant participants, contradictory evidence and any aggregate acceptance rule need later owner-reviewed policy.

A source review identified an additional epoch-time boundary: a late-recorded old fact must not be reassigned to the current epoch merely by presenting the current revision/reference. Following the distinct 5-failure red above, change/reopen set `reviewOpenedAt` to trusted server `recordedAt`, and record actions earlier than that opening return `review_occurrence_before_epoch` using exact `Temporal.Instant` ordering. An occurrence exactly at opening remains eligible. Returning from version v1 through v2 back to v1 does not resurrect its old decisions or admit an old occurrence as new approval. Existing history remains unchanged. Recording historical late evidence into an old epoch remains a future explicit, owner-reviewed capability; this increment must not relabel it as current approval. These source rules passed the selected unit run.

A further source review found that the server-recording clock itself could regress and move a new opening before an earlier committed approval. Following the distinct 7-failure red-time run above, the policy requires every command's `recordedAt` to be at least trusted `lastRecordedAt`, otherwise `review_time_conflict`, with revision/target mismatch precedence retained. Successful mutations advance the high-water mark to the exact supplied recording string. Nanosecond-backward changes/reopens fail; a time after the original opening but before a later mutation also fails. Equal instants, including differently written explicit offsets, are permitted and retain their source strings. Change/reopen cannot move opening backwards when the trusted loader's high-water coherence holds. Failed commands leave input history unchanged and produce no success receipt. Receipts retain exact previous/new openings and the previous high-water string as well as the current command recording time. These cases passed the selected unit run after actual red. No clock or shared authority API is added.

The prepared ordering test is a pure snapshot-sequencing expectation. It is not evidence that actual concurrent database operations have one winner. Transactional revision comparison, unique intended records, immutable history persistence and restore behavior require real PostgreSQL tests after the schema/base/allocator gates are resolved.

## Exposure and unresolved production gates

History and the approval projection above are proposed server-only values. No browser read DTO or route exists. Raw native recorder UUIDs must stay out of browser action/data contracts. Any future permitted display of a recorder's name/provenance needs a deliberate permission-safe projection and the Privacy owner's reviewed disclosure rules; server records must not be spread into serialized props.

Native auth/session freshness, CSRF, current reviewer capability, project/CRM/contact ceilings, same-project deliverable/version ownership and the selected client's actual project relationship remain real server checks. An input UUID is not proof of those relationships. Privacy subject relationships, store/writer/history inventory, actor disclosure, restrictions/retention and lifecycle adapters need owner review. These functions create no database record, access grant, financial action, task, reminder, message or other effect. References are validated/rendered as bounded plain data and never fetched. Existing assignment approval remains its own gated source policy until a narrow version/decision binding is agreed.

An idempotent service command envelope and its actual transactional history writer are also unimplemented. Pure optimistic revision rejection does not prove request deduplication or installed database concurrency. The persisted loader must establish coherent native-authorized state, including high-water/opening/history chronology, before any service exposes these policies. These later gates are not replaced by this unit source increment.

Future persistence must retain the original instant strings and the full supported fractional precision for `occurredAt`, `recordedAt`, opening/high-water values and receipt chronology. It must not silently round or truncate them in the database and then compare those altered values as though the original nanoseconds survived. The actual schema, transactional writer, fresh/upgrade/restore paths and exact round-trip comparisons require separate real storage evidence; no database representation or migration is allocated by this document.

Types, type-aware ESLint, Biome and combined/regression test selections remain unrun for this review increment. App/worker builds, actual storage/concurrency/recovery, native auth and UI workflows, Privacy inventory/disclosure/restriction integration and owner acceptance also remain open. The 43 passing cases establish only the declared selected pure unit behavior on the retained source; those broader gates remain unqualified.
