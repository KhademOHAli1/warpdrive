Every revision column uses `bigint(..., { mode: "number" })` and an explicit database range `0..9007199254740991` (`Number.MAX_SAFE_INTEGER`), with nullable previous revision permitted only for creation. A PostgreSQL `integer` cannot represent that contract. Local successor checks require `new = previous + 1`; overflow fails the proposed range. Existing pure lifecycle code already refuses an increment at the safe maximum. SQL checks/unique keys alone do not establish contiguous history, a matching current head, revision CAS or transaction atomicity.

Canonical references preserve existing IDs rather than names, email addresses or copied CRM bodies. Proposed `RESTRICT` behavior retains a visible dependency for physical deletion, subject to owner compatibility review before adoption. It supplies no current availability/visibility proof: soft deletion, archived deals/pipelines, accepted active staff and every authoritative parent still need actual native loaders/commands.

## Current lifecycle, without a new engine

The six exact states are `planned`, `active`, `on-hold`, `completed`, `canceled`, `archived`. An archived row requires `archivedFrom` from the five unarchived states; every other row requires null. The current `projectLifecycle.ts` policy-version-1 graph is:

| Action | Current allowed source and destination |
| --- | --- |
| `start` | planned to active |
| `hold` | active to on-hold |
| `resume` | on-hold to active |
| `complete` | active to completed |
| `cancel` | planned, active or on-hold to canceled |
| `archive` | Any unarchived state to archived, retaining that source |
| `restore` | Archived to its retained `archivedFrom` |
| `reopen` | Completed or canceled to planned |

Hold, cancel, archive, restore and reopen require a reason in the current policy. Creation is a distinct history action, not a lifecycle transition from a fabricated prior project. Its initial state and policy/version binding still need the create contract; this notation does not authorize arbitrary initial states. The existing reason boundary trims and bounds text to 2000 UTF-16 units, permits ordinary tab/newline/CR, rejects other C0/C1 controls and nonempty format-only reasons. Storage must preserve the validated policy receipt rather than invent a different reason normalization.

## Owner decisions that block a complete schema

1. **Protected reason placement.** Choose either the four-store variant's separately protected/redactable history payload or the proposed fifth `agency_project_history_content` store. The skeleton leaves the payload slot incomplete rather than restoring historical plaintext or inventing a crypto column. The fifth option has primary key `history_id` and NOT NULL `project_id`, plus a composite FK `(history_id, project_id)` to an explicitly unique `(history.id, history.project_id)` pair. Two independent FKs do not prove that the event and payload belong to the same project. At most one payload per event is structural; required insertion with the event remains transactional writer work. Initial absence must remain distinguishable from a later redacted/expired payload.
2. **Crypto and Privacy ownership.** Public `src/features/privacy/crypto.ts` defines a private `PrivacyContext` with required `caseId` and purposes `intake | decision | identity | job | policy`. `encryptPrivacy`, `decryptPrivacy` and `fingerprintPrivacy` are case-bound, not Agency interfaces. Its `VERSION = 1` is the packed ciphertext/AAD format version, not a persisted encryption-key version or key-rotation facility. No Agency purpose, project context, per-content key lifecycle or disposition API is present. Do not cast a project ID to `caseId`, invent a purpose/import, or declare erasure by dropping a shared-key reference. Exact representation, key references, rotation, backup/restore residuals and permitted disposal require the actual owner contract.
3. **Private replay comparison.** Select semantic fields and canonical serialization/version, actor/operation/intent domain binding, private fingerprint representation/encoding, purpose/key reference and rotation/replay policy. The draft selects no raw SHA or new fingerprint format. Define current-authorized recovery, changed-body conflict, deleted-result outcomes, tombstone comparison after content removal and behavior when old comparisons are unavailable. Never treat unavailable comparison as permission to recreate an old request. Tuple uniqueness supplies none of these semantics.
4. **Complete operation and revision vocabulary.** `create` and the eight lifecycle names are known. Exact title/link-edit, owner-transfer, membership grant/revoke/grant-change names and fact/version contracts are still open. Decide whether/how each advances the project revision, binds a request receipt and records old/new target/grants/owner/CRM relationships. The lifecycle-only history columns cannot be claimed to retain all membership/ownership edits. Do not solve this by an unconstrained raw-input JSON history, a generic event engine, or silently omitting those writers. Complete finite database action/operation constraints remain absent until that decision.
5. **Title bound.** The reviewed proposal says 255 UTF-16 code units. JavaScript/Zod string length counts UTF-16 units; PostgreSQL `char_length` and `varchar(255)` count characters, so 255 supplementary characters occupy 510 UTF-16 units. Adopting those SQL expressions alone would change the reviewed bound. Choose a reviewed database expression plus matching ingress tests for the existing bound, or explicitly amend the product contract and obtain review. The notation leaves SQL title validation open; it does not silently switch units, add an unreviewed helper function or claim database parity. Required/nonblank/control and normalization rules for the eventual title ingress also need an explicit contract.
6. **Retention and physical deletion.** Decide retained/redacted/transferred/deleted outcomes for canonical parent, owner, member, actor, history and request dependencies. Current soft-delete compatibility does not prove physical erasure. A restrictive FK failure must become a bounded non-probing dependency outcome, never a hidden-project name or raw SQL error. No cascade, silent anchor `SET NULL`, purge interval, hold exception, disposition writer or indefinite legal retention is selected. Ordinary fact immutability and narrowly authorized later lifecycle changes need distinct reviewed SQL/authority rules.
7. **Native admission and concurrency.** Finalize project owner/member/native-admin semantics, all old/new CRM ceilings and staff eligibility, membership/owner management, authority generation/lock order and participating revocation writers. Existing Privacy `withPrivacyAuthority` is for Privacy capabilities/cases (including `case.assign`); it is not a project authority or generic writer/restriction fence. The implemented global `project.create` registration and default-off module setting do not fill those contracts. No client boolean, FK or pure receipt supplies native admission or through-commit protection.
8. **Canonical lineage, inventory and allocation.** Platform must select the accepted combined base and allocate the forward migration/journal/snapshot. This document reserves no number or canonical lineage. Privacy must classify every adopted physical store, exact real writers and copies, with explicit unsupported discovery coverage until actual readers qualify. Writer IDs/source digests cannot be finalized before those writers exist. If selected, the fifth store needs separate owner acceptance and coverage; historical four-store conditional review does not accept it.
