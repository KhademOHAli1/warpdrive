`src/features/privacy/registry.ts` is the capability boundary. ## Discovery and review controls

The scanner reads production TypeScript/TSX under `src/` and `scripts/`, excluding named tests, fixtures, DB test infrastructure and known test helpers. TypeScript AST discovery identifies:

- Actual `pgTable` declarations (including import aliases) and named `pgSchema` tables, including schema files not yet exported from the schema barrel.
- Insert/update/delete/execute boundaries, raw SQL `q`/`query` wrappers, file writes and S3 upload/copy/delete boundaries.
- Queue declarations and pg-boss enqueue/worker/schedule calls, including the generic import queue dispatcher as an explicit dynamic boundary.
- Object-key builders, literal upload namespace prefixes, and the file entity namespace allowlist.
- Fetch/SMTP and known PostHog SDK boundaries, browser storage reads/writes, in-memory collections, query-cache mutations and console log sinks.
- SHA-256 source-review IDs for discovered boundary files and named boundary configuration. Changing a queued payload or an existing object-key helper therefore requires fresh review even if its method/queue name stays constant.

The scan is conservative. A hash `.update` and a transient `Map.delete` can appear alongside persistent DB writers. Counts are boundary signatures, not a count of personal-data databases. Same-origin browser fetches remain classified so a later destination change cannot inherit an unchecked declaration. A dynamic import queue is not falsely described as a newly resolved fixed queue.

The PostgreSQL test independently inspects actual `public` tables after real migrations, then creates an undeclared synthetic table and verifies rejection. It does not start pg-boss or qualify its installed schema. pg-boss metadata and Drizzle migration metadata have explicit operational declarations. Their actual installed versions, payload history and expiry need runtime/operator reconciliation.

The scanner is a regression guard, not a general proof about arbitrary JavaScript, opaque SDK internals, generated SQL, deployment scripts or a running installation. A new persistence/recipient technology or wrapper requires an explicit scanner rule and a failing example before it may be used. Source imports and third-party behavior still require code review. Unknown runtime capabilities remain blocked by the registry contract. Keep deployment inventory and actual PostgreSQL/object-store reconciliation as separate release gates.

## Test-first evidence and contribution rule

The initial registry suite failed because the registry did not exist. Later negative tests failed for same-queue payload drift, same-helper namespace drift, previously untracked PostHog/cache/browser reads, boundary-configuration drift, aliased/non-public table discovery, malformed declarations, unavailable-source handling and cancellation; production rules were added only after those relevant failures were observed. The first live table-catalog invocation failed during test infrastructure startup because the default Docker socket was unavailable. With the existing disposable `colima-warpdrive` context selected per command, both real-PostgreSQL tests passed (12.30 seconds, pinned Bun 1.4.4/Vitest 5.0.5). Those assertions are baseline integration verification of the implemented registry; they were not reported as failing-before-production behavior. Existing raw SQL and read-only baseline checks are verification, not claims of new runtime behavior.

Tests also detected real concurrent development: `authorityManagement.ts`, case/intake writer additions and new schema migrations produced missing IDs before their reviewed declarations were incorporated. Do not update literal IDs merely to silence a failure. Review the store, writer, payload, recipient, subject relationship, disclosure rules, retention and supported proof first. Add a failing scanner example for any new wrapper/technology. Capability status may change to `supported` only with the owning task's exact-revision tests and evidence.

The primary implementation evidence register owns final command results, exact commit/tree, full CI and acceptance status. No user interface was changed by this inventory task; there is no new locale text or live transport/erasure action to qualify here.

2. Inspect exact calls and dependencies: store/namespace, subject versus owner relationship, credentials, current/history copies, payloads, destination, authority, retention and proof. Review changed behavior before replacing a source digest.
3. Add only reviewed literal IDs to the matching `registryIds*.ts` classification. If purpose or constraints differ, add a complete explicit entry in `registryEntries.ts`. Separate runtime secrets, source metadata and staging references; opaque references are not automatically anonymous.
4. For a new persistence/transport wrapper or import alias, observe a failing discovery example before extending the owning AST rule. Existing wrappers do not prove coverage of an unknown technology.
5. Keep generic lifecycle capabilities unsupported until the owning task has complete current-authority, reviewed-scope, storage/transport, failure and retention evidence. Candidate readers, projections and archive codecs are narrower contracts.
6. Freeze relevant source, run inventory unit and real migrated-PostgreSQL catalog tests, then formatting/type/lint checks. Regenerate `docs/privacy-inventory-report.json` only with successful CLI exit and empty missing/invalid lists. Bind it to the candidate commit and separate full CI/installation evidence.

After a successful standalone CLI run, compare fresh output with `bun scripts/privacy-inventory.ts | diff -u docs/privacy-inventory-report.json -`. Any later source change needs a fresh report. Its fingerprint covers scanned source and does not replace exact-revision CI or installed acceptance.
