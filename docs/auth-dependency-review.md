# Authentication dependency qualification and remaining advisories

Reviewed 31 October 2026 from source baseline `01dd1dd`, with release qualification repeated after merging main `d37518a` (v1.4.0) and its upstream import/permission updates. The dependency inventory below retains its recorded review checkpoint. This is dependency and protocol qualification, not a claim that the repository has no vulnerabilities.

## Result

- Better Auth core, Drizzle adapter and passkey plugin are pinned to **1.7.14**. Their distributed licenses are MIT. Nodemailer 10.3.1 and QRCode 1.5.4 support local transactional delivery and local QR rendering.
- `bun audit --json` reported **49 scanner entries across 17 package names** in the baseline lockfile. Installing the authentication dependencies produced the exact same 49 package/advisory pairs, with no additional advisory IDs at that checkpoint.
- Targeted compatible overrides reduced this to **9 entries across 6 package names**: five entries on MinIO runtime dependency paths and four on development-tool paths. The remaining entries and observed reachability limits are explicitly open below. Scanner output is a dependency inventory; a clean result would still not establish absence of vulnerabilities.
- At the installation checkpoint, Bun **1.4.2** successfully installed and re-read the resulting version-3 lockfile using `bun install --frozen-lockfile`. The authentication dependency change did not upgrade the framework major or unrelated application declarations. The existing Next.js patch remains intact.
- Final merged-tree runtime qualification uses pinned **Bun 1.4.4**, including frozen installation and the production application/server/operator builds. Current complete suite totals and local checks are recorded in the [implementation report](auth-implementation-report.md), separately from the earlier checkpoint. This runtime patch fixes the native `ws` message-cap behavior reproduced on 1.4.2; see [runtime compatibility](bun-runtime-compatibility.md).
- Bun imports of Better Auth, its passkey plugin, Tiptap/ProseMirror, MinIO and isomorphic DOMPurify passed after the overrides. Local source and protocol qualification does not activate or verify an installation's external providers, SMTP delivery or physical passkey devices.

The inventory was obtained with `bun audit --json`, lockfile comparison, `bun why <package>`, current npm package metadata, GitHub advisory records and inspection of the installed package call sites. Counts describe the recorded review checkpoint; rerun the commands before release.

## Authentication protocol qualification

The migration adds application safeguards around native Better Auth behavior. The following are actual Bun tests using disposable PostgreSQL, not mocked database claims:

- Hash-only session storage: new credentials are returned to the issuing request, digest-only rows are persisted, credential lookups restore only caller-presented values, and ID/list reads redact token values. Stored hashes and row IDs do not authenticate. Transaction adapters are recursively wrapped; token rotation, bulk operations and atomic consumption are covered.
- Existing soft revocation: configured `revokedAt` filtering prevents a signed native session cookie from working after database revocation. Unsupported OR-session filters are rejected rather than allowing an appended liveness clause to be bypassed.
- Current-device logout: the existing form now submits through same-origin POST with matching cookie/form CSRF tokens. GET, cross-site or missing-origin requests cannot mutate sessions. Only the presented opaque credential's hash is revoked; other devices remain signed in. Database row IDs and stored digests cannot be used as logout credentials.
- Recovery: raw codes are shown separately from stored hashes. Submitting a leaked stored digest fails. Concurrent same-code redemption yields exactly one success; replay fails and remaining codes continue to work.
- Passkeys: an ephemeral P-256 synthetic authenticator sends a CBOR none-attestation and signed WebAuthn assertions through the actual HTTP handler. User-verifying registration/login work; wrong origins, missing user verification and reused ceremonies fail. This qualifies protocol enforcement, not physical device compatibility or a browser's native passkey UX.
- Factor enrollment: a failing real-protocol regression showed that a pending password session could enroll another passkey after a strong factor existed. The corrected policy permits pending-session bootstrap only for the first strong factor. Tests now deny further passkey enrollment and confirmed-TOTP-secret retrieval from an older weak session. Enrollment itself does not upgrade the password session.
- TOTP: the native credential/enrollment flow issues an authenticator URI and ten hash-stored recovery codes, requires confirmation, rotates the initial session, accepts Persian digits and denies application access until verification. Wrong codes, consumed challenges and trusted-device bypasses are rejected. Native 1.7.14 does not itself prevent one valid TOTP from redeeming different challenges; its verifier accepts the current 30-second counter and adjacent counters. A real failing test reproduced two successful independent concurrent challenges with one code. The application now adds a 120-second atomic reservation of a keyed code digest per factor before its final assurance grant. The passing regression permits exactly one challenge to gain access, revokes the loser's new pending session, and denies reused-code step-up without renewing the existing session's freshness. Storage tests cover 20 concurrent reservations, Persian-digit equivalence, expiry, factor isolation, pruning and cancellation.
- OIDC: a real loopback HTTP provider serves discovery, authorization, token and RSA JWKS endpoints. Actual native handlers emit S256 PKCE and nonce, exchange the code and validate the signed ID token. An invited verified identity retains its CRM UUID and consumes its invitation once. Missing invitations, wrong invited email, state/nonce/issuer/audience/signature, bad PKCE and callback replay are denied. Email-only implicit linking is denied; explicit fresh same-email linking works, while stale or different-email linking fails. Loopback HTTP is supplied only through direct test configuration after the production HTTPS-issuer validation boundary; no deployment or real Google/Microsoft tenant acceptance is implied.
- OIDC discovery pinning: native 1.7.14 accepts the discovery document's issuer without comparing it to the configured issuer. A failing real-provider test reproduced that mismatch. The application's final provider guard now checks the native cached metadata against the exact configured issuer at initialization and after discovery retries, before authorization, explicit linking, direct-ID-token authentication or callback handling. A successful metadata fetch cannot silently redefine the configured provider's issuer. Correct metadata still passes the full flow. This enforces the [Discovery 1.0 provider-validation requirement](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderConfigurationValidation) without a separate discovery fetch or additional user-controlled URL input.
- Shared abuse control: PostgreSQL upserts enforce budgets across independent limiter instances. Tests cover concurrent attempts, account/IP/endpoint rotation, untrusted forwarding headers, unknown-IP aggregation, window reset and aborted requests. A proxy header is trusted only when configured; the operator must also keep the app behind that proxy and make it overwrite the header with one client address.
- Concurrent recovery: native HTTP verification now derives an account lock from an unauthenticated passkey credential ID or native two-factor challenge, then re-reads and verifies the actual proof inside the same transaction. Lock selection never grants authentication. Real PostgreSQL regressions hold the operator's common advisory lock, verify that both proof methods wait, remove the factor, and confirm that the old proof fails after release. Current-session and proof-account locks are acquired in sorted order.
- Anonymous native transactions: password resets and provider callbacks also run through the transaction-local adapter. Real row-lock barriers show the global MCP-grant lock remains held through native credential/profile mutation and notification commit. A successful reset revokes old access/refresh grants and consumes old authorization codes before another grant-lock holder enters. A real notification-queue failure originally committed a changed password even when the handler returned 500; the gateway now rolls back server-error responses, leaving the password/reset token/grants available for safe retry. Authentication denials retain their rate-limit writes.

Upstream passkey verification does not require user verification by default, and native two-factor hooks do not cover every social/passwordless method. These properties are handled by the application's verification hooks and workflow-access policy; enabling plugins alone is not sufficient. [Passkey plugin](https://better-auth.com/docs/plugins/passkey), [2FA behavior](https://better-auth.com/docs/plugins/2fa).

## Reproduction and release boundary

Run `bun install --frozen-lockfile`, `bun audit --json`, relevant `bun why` queries, scoped authentication unit/integration tests and the complete build/test checks before accepting a release. Preserve the review date and actual remaining results; do not convert the open findings into an empty allowlist or remove dependency entries to silence the scanner.

Package lifecycle scripts remain subject to Bun's trust policy. The reviewed installation did not manually enable blocked postinstall scripts merely to obtain a green audit result. Runtime import checks passed without doing so.

Any later package update invalidates the corresponding installed-version and qualification evidence. Final release notes must identify remaining advisories and any external-provider, browser/device or deployment checks that were not executed.
