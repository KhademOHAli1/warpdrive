## Filter increment: implemented, awaiting runtime qualification

The new filter node is wired through the schema, factory, insertable catalog, configuration/validation, copy, typed output mapping, execution, routing, draft simulation, publication review and live-run review. It uses an ordinary next edge. A true matchesFilter output continues; false commits a successful terminal run with its Filter receipt and no downstream cursor. Missing/invalid operands remain execution failures, distinct from a valid non-match. The editor reuses predicate controls with localized Filter-specific continuation/termination copy. Node presentation and inspector exhaustive maps were handled by the corresponding owners.

Qualification evidence: new14 model and4 localized editor cases passed. The final focused12-file invocation passed122/122 in7.79seconds; prior nonoverlapping copy/group-evaluation/publication/live-review regression cases passed separately. Warning-mode execution used one worker,initial51% reported memory headroom,sampled owned peak1,127,200KiB,and terminal process-group cleanup. Scoped Biome32 returned exit0 with5 informational template-style suggestions; git diff whitespace check passed. Original functional14-failure baseline and4-failure editor baseline remain in the parent work/filter-checks logs.

Seven actual PostgreSQL cases are prepared in src/features/workflows/filter.integration.test.ts but **have not been run**: both live outcomes with competing deliveries,both persisted simulation outcomes,a needed-missing-operand failure,and both rollback-contained draft outcomes. Whole-application type generation/TSC,typed lint and privacy source-inventory qualification remain the parent's candidate checks. No live provider or installed runtime acceptance is claimed.

This first functional slice deliberately shares the reviewed predicate grammar: flat exists/equals/notEquals/contains,and grouped predicates adding isEmpty with AND/OR. Full Twenty operator/type parity remains open: its broader generic filter operand enum includes negative contains,numeric comparisons,date ordering/relative/past/future/today and vector search. Those controls are not advertised as supported. The remaining matrix rows still require their concrete handlers and configuration flows; the Filter increment does not close overall block parity.

## Second increment: ordered If/Else, record creation and richer Delay

- **If/Else (A11):** evaluate conditions in order and continue along the first matching branch or Else. An unconnected chosen branch ends successfully. Removing a branch removes only that outgoing connection; the downstream node stays on the canvas. This uses the same bounded operators as Filter.
- **Create Record (A1):** create a deal, lead, person, organization or task through the native CRM service under the run actor's permissions. Supports mapped built-in fields and typed record IDs as outputs. Creation participates in the workflow transaction; simulations roll it back. Custom and installed object support remain open.
- **Delay (A12):** wait for a bounded days/hours/minutes/seconds duration or a scheduled date/time, including typed variables. The engine resolves the time once, persists it, and resumes through the existing queue and recovery path. Older saved delays keep their behavior.
- The canvas shows a temporary empty node when inserting a step from a free connector. The picker opens without changing zoom, and closing it discards the temporary node without changing the draft.

Verification: 568 focused tests across 33 files passed, including branch selection, mapping, inspector behavior, and privacy inventory checks. Two additional PostgreSQL cases cover first-match record creation with competing deliveries and simulation rollback. Native PostgreSQL and rendered browser qualification were not run on the shared workstation.

The gap tables below preserve the initial audit. Apply these increment notes when reading their statuses.

## Independently implementable first increments

The following order exposes real working blocks without waiting for new external credentials. It does not mark the other catalog entries complete.

1. **Filter vertical slice:** new filter node schema/profile and ConditionFields reuse; executeFilter from the existing bounded evaluator; stop-success branch directive; typed result; factory/palette/inspector/save/reload/publish/run integration. Focused tests should prove false terminates before a task effect and true continues exactly once, including grouped short circuit and invalid stored config.
2. **Delay contract parity:** proposed normalizeWorkflowDuration/resolveWorkflowDeadline helpers; days/hours/minutes/seconds plus variable inputs; reuse durable time wait; define past-date policy and simulation behavior explicitly. Test boundary/overflow/temporal binding and deadline recovery. Fixed-instant support already exists in live runtime and must not regress.
3. **Ordered If/Else branches:** proposed selectMatchingBranch pure function and branch config validation; reuse predicate evaluation. Then wire stable branch IDs/ports into save, graph, editor and runtime. Pure tests can precede DB work, but the block is not complete until branch selection drives real persisted execution.
4. **Record adapters:** implement a finite, typed adapter per real Warpdrive object, starting with the existing task specialization and contacts/deals rather than pretending every arbitrary Twenty custom object exists. Add create/update/delete/find forms and handlers, then unique-key upsert and authorized pick. Pure unique-key/field-mask/filter planning helpers can be delegated independently; domain write integration needs actor/replay tests.
5. **General wait/effect foundation:** own schema/migration and executor protocol together. Form/event waits and iterator frames need durable state; send/draft/calendar/HTTP/code/AI/chat/function slices then use the same execution-key/effect receipts. No live provider effect is exercised by this audit.

All new helper/function names above are proposals. Root should assign file ownership before implementation because these changes cross the current action schema, executor, metadata and UI contract.

## Minimum proof for each advertised block

A block is functional when its actual editor flow configures every required field, persists/reloads without dropping settings, validates server-side, publishes at an immutable version, executes under current authority, and records usable output/error. Pure unit tests alone cover only pure helpers. Mutating blocks additionally need rollback/idempotency/concurrent retry evidence; external providers need real adapter contract and safe acceptance evidence at an authorized revision; wait/loop blocks need crash/cancel/replay/race evidence. No service or provider acceptance is claimed here.

Existing reusable focused suites include conditionGroupsEvaluation/Runtime, delay/fixedInstantWait/durationPublicAdmission, mappingCustomRuntime, configurationRuntime, executionSafety, lifecycleAuthority, runControl and runRetry. Their existence is not qualification of new node types.
