### Planned app and channel journeys

These are design-only flow maps. They do not create installable apps or enable a channel:

1. **Connection-backed rule:** discover supported capability, review personal/shared account, authorize minimal capabilities, select stable resource IDs/disclosure fields, save draft, preview a synthetic event, activate an immutable rule version, inspect delivery history, then pause/reconnect/remove with held work explained. Member actions require explicit delegation; administrators still cannot bypass private data or app-grant ceilings.
2. **Private application:** discover/import a bounded package, inspect publisher identity evidence and exact pinned version, review requested CRM/outbound/resource/egress permissions, install only on a qualified isolation profile, configure connections, run a no-effect preview, then enable. Missing isolation is a blocking prerequisite, not an ignored warning. Package availability and installation never mean a provider account is authorized.
3. **Update:** inspect old/new version and permission/schema/egress difference, preserve the current version while reviewing, consent only to the explicit expansion, run qualified migration/recovery, then activate. Failed migration holds the update with a recovery path; no silent scope widening or unsupported rollback promise.
4. **Disable/uninstall:** distinguish stopping admission, in-flight external outcomes, removal of credentials/package and retention of CRM/app data. Default confirmation does not promise recall of accepted messages or deletion of provider content. Ordinary member cannot uninstall a shared app or clear a security hold.
5. **Publisher/marketplace:** submission, review/quarantine, provenance/version/support evidence and publication remain separately gated. A catalog logo, generated client package or self-reported name must not receive a verified-publisher badge.

State refresh follows server authority: update from a persisted result and refresh current facts, retain conflicts/unknowns, and never optimistically declare remote revoke/send complete. A successful local save may say “saved”; it cannot say the provider accepted an effect. Recheck grant revisions on server actions/jobs, not only when opening the dialog. UI state is explanatory and cannot enforce authority by itself.

Keyboard/responsive requirements for each implemented increment: logical DOM reading order; visible labels; focus trap and focus return; Escape dismissal where valid; arrow keys through Tabs/Select; selected state announced; live result text without repeated announcements; target at least the current compact adapter size; no horizontal overflow at 320/390/768/1440 px. Light/dark and reduced-motion review remain browser acceptance work, not a result established by these source patterns.

## UX-004: Farsi-first truth-state copy

The six availability dimensions are independent facts. A provider can be implemented and configured while no account is authorized; an authorized account can be unhealthy or lack a selected resource; a healthy access check can coexist with no live-provider qualification. Display a concise primary state and a bounded explanation relevant to the next decision. Do not display six badges on every row or leak source/build details into an ordinary connect flow. Exact qualification profile/date belongs in support details where useful.

The following keys are semantic proposals, not existing runtime translation keys. Persian wording is drafted first; German and English preserve the same scope. Tokens such as `{provider}`, `{account}`, `{time}`, `{scope}`, `{done}` and `{total}` are validated/escaped and formatted by current locale preferences. Sensitive names/IDs appear only in authorized DTOs.

### Regional and accessibility review scenarios

Current locale preferences store locale, calendar, timeZone and optional numberingSystem separately (`src/features/i18n/preferences.ts:11-31`). `useFormatters.ts:13-27` passes all four; Regional controls select language, timezone and Persian/Gregorian calendar (`LanguageSettings.tsx:60-103`). New integration surfaces must reuse them, not infer preferences from provider country or UI language.

- Farsi with Latin digits, Gregorian calendar and Europe/Berlin time: Persian prose/RTL layout, unchanged ASCII provider IDs and URL, user-selected date/time display.
- German with Iranian calendar and Asia/Tehran time: German copy, Persian-calendar date semantics, explicit zone; no automatic conversion of an authored Iranian recurrence into a Gregorian rule.
- Farsi with Persian digits and UTC: counters/times follow chosen numbering; copyable URLs/scopes/IDs remain exact ASCII within `dir=ltr`/`bdi` and are never transliterated.
- All-day date versus instant: a date-only resource/schedule retains its civil date. Changing UI zone cannot move an all-day event to another day. Display time-zone labels for actual instants and scheduled sends where a different zone changes the user's decision.
- Switching language during a pending request changes messages via translation keys without resetting account/resource choice or changing the request payload. A server conflict is not erased by rerender.
- Mixed-direction account/channel names, long German labels, missing owner/date, no resources, permission denied and unknown outcome: check reading order, wrapping, focus return, visible status text and no color-only meaning.

These are required future browser/evaluation scenarios, not newly passing checks. Copy review can assess intended wording; rendered selection, formatting and assistive-technology behavior need implementation evidence.
