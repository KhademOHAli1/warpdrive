## ARCH-006 decision: one canonical fact and one execution path

The canonical domain service that commits a CRM mutation owns its durable event fact. Add a shared transaction-only event writer and call it inside the same transaction as the mutation and its audit history. Do not emit independent facts from UI server actions, tRPC, MCP, import wrappers or provider callbacks if those paths already call the canonical service. Wrappers may supply authenticated provenance and a stable command identity; the service determines the event type and record changes actually committed.

For the first stage-change example, append a fact only when the committed stage ID differs. A same-stage board reorder does not become a stage-change fact. A failed permission check, failed CAS, failed event insert, thrown error, aborted transaction or rolled-back simulation produces no committed fact and no provider intent. If event persistence fails, roll back the domain mutation instead of reporting a successful mutation with lost automation intent. Existing board invalidation remains in that transaction and keeps its current payload semantics.

The event writer accepts a Drizzle transaction, not an optional root DB handle that could silently open an unrelated transaction. Its input is validated once at that boundary, takes required `AbortSignal`, returns the project's Result/error conventions, and performs bounded database work only. It never enqueues a job, resolves credentials, renders unrestricted CRM text or calls a provider inside the mutation transaction.

Committed facts are immutable. Dispatch state, routing progress, admissions, effects and attempts live separately; a fact must not have a single global delivered flag that allows the first subscriber to consume it for every other subscriber. Retention may remove payloads under a reviewed policy while retaining the minimal IDs/tombstones needed for bounded deduplication. A retention policy must state the maximum supported replay horizon; a deleted dedup tombstone cannot support an unlimited duplicate-suppression claim.

Keep a separate `executionContextId` and an operator-controlled `externalEffectsEnabled`
guard for the current running environment. A clone/test/restore starts with a fresh execution
context and external effects disabled. Existing fact/admission/effect IDs and origin
`sourceContext` remain unchanged, so restoration cannot re-key old work into fresh deliveries.
An effect records the execution context where it was admitted/prepared. A mismatched context
blocks sending, including recovered ready/sending rows. Enabling a restored production context
requires a finite recovery review of leases, known/unknown outcomes, authorization, idempotency
windows and explicit selected work; changing the context or enable flag alone never releases
old effects. Local qualification retains no authority for actual external effects; protocol fixtures use explicitly isolated loopback endpoints. The present profile does not claim an enforced general network sandbox, which remains separate SDK qualification.

Wire timestamps use UTC ISO strings; IDs, revisions and counters remain locale-neutral. FA/DE/EN display language, Iranian/Gregorian calendar, numbering and time zone are independent presentation preferences. Rendering may convert the timestamps, but cannot reinterpret event order, provider identifiers or schedule instants.

An exact COMMIT timestamp is not currently available in the inspected schema. Do not label `recordedAt` as an exact commit timestamp. EVT-002 must preserve the recorded/observed distinction in its acceptance evidence, or explicitly choose and qualify an actual commit-time mechanism if exact physical commit time becomes a requirement. This architecture document alone does not satisfy that implementation criterion.

### Dispatch, admission and fan-out

One event dispatcher is registered through the existing `registerAllJobs`/pg-boss stack. New named jobs may be added to that stack when needed; no second broker, independent scheduler, parallel rule engine or alternate retry store is introduced. Durable PostgreSQL rows are authoritative. pg-boss jobs carry IDs and are wakeups, not the sole copy of intent or credential/payload snapshots.

1. A bounded scan claims committed undispatched/partially routed facts with a lease and fencing token. The initial local default is at most 100 facts per scan and 100 subscriber admissions per transaction. These defaults are named configuration/contract values with validation, not silent unbounded loops.
2. In a short transaction, resolve applicable subscriptions against their persisted activation boundary and pin the immutable rule/workflow version. Persist admission identity, routing progress and any connector effect intent atomically. Partial fan-out resumes from persisted state; an enqueue acknowledgement does not mean all subscribers were admitted or delivered.
3. Automatic workflow subscribers use a new typed event-admission adapter into the existing workflow run/version/cursor model. They must not fake a fresh manual UI request key on each retry. Manual admission retains its present API and identity rules. Record-trigger payloads and uniqueness constraints require an explicit schema extension and tests; they are not implemented by the current `admitManualRun`.
4. After the admission/effect transaction commits, nudge the existing worker. A lost or duplicate nudge is harmless because boot and bounded periodic reconciliation find the persisted ready work. A queue send followed by process death before local acknowledgement may produce another queue job, so execution must re-read the same durable intent and use database uniqueness/fencing.
5. Reuse the workflow registry, typed bindings, graph validation, permission evaluation and immutable versions for rule/action execution. Channel-specific renderers and provider adapters are actions, not another expression language or engine. Mail/SMS/Slack actions share event/admission/effect semantics; domain adapters retain their transport-specific behavior and ownership.

Activation defaults to future events: store an activation watermark from the source cursor and require an explicit finite replay selection to consider earlier facts. The watermark is a logical source allocation boundary, not an exact wall-clock COMMIT cutoff. A fact allocated before activation but committed later is still before that watermark; the UI/docs must not promise “every transaction committed after this clock time.” Pin each `(event, subscription)` to one rule version on first admission, so a later rule edit cannot silently rerender or replay the same event. Activation/disable/first admission races need a deterministic transactional policy and real-DB cases in EVT-013; this contract chooses future-only admission and immutable pins, not a complete schema/locking implementation.

NOTIFY may still be used as an optional low-latency wakeup after/with durable writes. Losing that signal does not lose the fact. The existing socket channel versions and per-socket sequence numbers never become event IDs, delivery IDs or integration cursors.

## ARCH-007 decision: at-least-once processing and explicit effects

Processing and wakeups are at least once. Local uniqueness and serialized state transitions prevent duplicate local admission/effect application. External networks can accept a request while the sender loses the response; this contract does not promise exactly-once external effects.

### Identities and deduplication

| Identity               | Logical unique key and behavior                                                                                                                                                                                                                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Domain fact            | `eventId`; where the domain command supports retries, also unique `(sourceContext, commandIdentity, eventOrdinal)`. CAS/no-op behavior remains domain-specific. Never deduplicate only by record ID, payload hash, stage pair or a time bucket, which would erase legitimate repeated moves.          |
| Subscription admission | Unique `(sourceContext, eventId, subscriptionId)` with pinned immutable subscription/rule version. A version edit does not create a second admission for the same fact. Explicit approved replay records a replay operation and its intent; default replay preserves this key.                        |
| Automatic workflow run | Unique source admission ID mapped to a run and pinned workflow version. Current manual `(workflowId, actorId, requestKey)` remains separate. Add a source-admission FK/key rather than inventing a random manual request key on recovery.                                                             |
| Database step          | Existing unique `(runId, nodeId)` while graphs execute a node at most once. A future loop/iterator must add an explicit bounded iteration identity before reusing that key.                                                                                                                           |
| External effect        | Stable `(admissionId, actionNodeId, effectOrdinal, connectionId, destinationId)` plus a server effect ID. Credential generation and retry count do not create a new logical effect. A separate explicitly authorized resend creates a new effect linked to the original, with duplicate risk visible. |
| Attempt                | Unique `(effectId, attemptNumber)`, lease/fencing token and start/result timestamps. Attempts may multiply; the intended effect identity stays stable. Upstream idempotency keys are derived from the stable effect only where that adapter supports and qualifies them.                              |

Keys are backed by database constraints, not only in-memory sets or `singletonKey` job options. Provider deduplication guarantees and expiry windows are adapter-specific evidence. A queue ID, HTTP success code or provider “accepted” response does not prove downstream delivery/read/receipt.

### Database effects versus network effects

For the existing supported database-only workflow actions, keep effect, step completion and cursor advancement in one transaction under the run lock. A crash rolls them all back or commits them together. Simulation uses the current rolled-back savepoint strategy only for such database-only actions; it does not justify executing network actions inside that savepoint.

For external actions, the workflow step transaction persists the effect intent and a waiting/result binding, then commits. Provider I/O runs outside the domain/workflow row transaction. Completion or failure re-enters a short transaction guarded by effect ID, attempt identity and fencing token; it persists sanitized outcome and resumes the same workflow cursor according to the action contract. A crash cannot require reconstructing intent from an untrusted log or recomputing a new payload from a changed rule.

Before send-start, prepare the exact bounded business request once under the current
source-record, field-projection and destination authorization decision. Persist an immutable
prepared request, its canonical byte/hash/version, destination/account identity and authorized
field provenance with the effect. Store only the allowlisted minimal content needed for the
request, encrypted where it contains private content, never a complete CRM record. Queue jobs
and logs carry IDs/hash only. The sealed representation covers the provider operation, stable destination, business
body/query and content/idempotency semantics. It excludes authorization headers, cookies,
SMTP authentication, credential fields wherever encoded in a form/query/body, broker invocation credentials and transport signatures/nonces. The broker
injects current permitted credentials at execution, so credential rotation cannot leak secrets
into prepared storage or require a new business body. Transport-only timestamps/signatures may
change; the adapter must prove that the canonical business hash and destination remain equal.
The first preparation commits before network I/O; retries use
those same request bytes and the same qualified provider idempotency key. A changed record,
rule label or template never silently rerenders an existing effect under that key. A hash/body
mismatch fails closed. Fresh authority checks still run before each retry; tightened policy or
lost visibility blocks the prepared request rather than broadening disclosure. A deliberately
changed body/destination is a new explicitly reviewed effect, linked to the original with the
possible duplicate consequence visible. Old prepared payload compatibility and retention are
bounded; a provider idempotency-window expiry cannot make an ambiguous resend safe.

The adapter classifies operations as no-effect reads, idempotent writes with a qualified stable key, or non-idempotent writes requiring reconciliation/review. The provider method and response define definite rejection versus ambiguous acceptance. Do not generalize Gmail's current 4xx/Message-ID behavior to Slack, SMS, SMTP, calls or financial writes. Provider-visible payload is rendered from the immutable allowlisted rule fields only after current authorization/disclosure checks; durable intent stores IDs and allowed metadata, not an unrestricted CRM snapshot.

### Delivery states and transitions

| State                   | Permitted behavior                                                                                                                               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ready`                 | Eligible durable intent; no network attempt has begun.                                                                                           |
| `leased`                | One fenced worker is preparing/checking the intent. Expired lease before send-start returns to ready.                                            |
| `retry_wait`            | A definitely safe retry is due later; stores bounded next-attempt time and sanitized cause.                                                      |
| `blocked_authorization` | Role, grant, app, connection, scope or destination no longer permits execution. No send. Reauthorization does not silently release old work.     |
| `paused`                | Explicitly held pending intent, separate from authorization failure; records the controlling rule/connection generation.                         |
| `sending`               | Send-start was committed before provider I/O. Worker death/timeout/cancellation after this point is potentially ambiguous.                       |
| `confirmed`             | Qualified adapter evidence confirms the provider accepted the defined effect. A receipt lifecycle, if supported, is separate and may later fail. |
| `failed`                | Definite terminal rejection, exhausted safe retry budget or malformed/unsupported input, with a stable actionable reason.                        |
| `unknown`               | Acceptance cannot be determined. Reconcile with a bounded provider-specific read or hold for explicit human review. No blind automatic resend.   |
| `cancelled`             | Effect was prevented before send-start or remaining future work was cancelled. It does not assert an already-started request was recalled.       |

These are semantic delivery states; they do not replace the existing connection lifecycle or current workflow run status enum. Implementation may use separate state/result columns, but must retain the distinctions in DTOs and evidence. Never overwrite a known remote success as “never sent” just because a late cancellation or stale worker acknowledgement arrives.

### Bounds, ordering, recovery and authority

- **Ordering**: preserve source aggregate revisions and serialize each local workflow run. No global wall-clock order or across-destination/provider delivery order is promised. The first channel action requires no strict external ordering. If a rule needs order, opt it into a bounded `(subscription, aggregate, destination)` lane; a prior unknown blocks that lane until reviewed, expired by explicit policy or cancelled. Do not hold unrelated destinations hostage. Event timestamp sorting is not a concurrency guarantee.
- **Retries**: initial local delivery default is at most eight safe attempts within 24 hours of first eligibility, base delay five seconds with bounded full jitter and a 15-minute exponential cap. A valid provider Retry-After is a minimum delay, even above that cap; if it exceeds the remaining horizon, park with an actionable reason instead of retrying early. Adapter stricter budgets win. Authentication/configuration/unsupported-input failures block or fail rather than consume a fast retry loop. Values require deterministic clock tests in EVT-008; they are not current runtime settings.
- **Leases and I/O**: every handler combines pg-boss cancellation with a finite action deadline. Proposed local defaults are a 45-second handler budget, at most 30 seconds per provider request, and a 90-second durable effect lease. Recheck cancellation after non-signal-aware awaits. A stale fencing token cannot acknowledge or mutate the current attempt. Once a send-start stamp exists, lease expiry does not make a fresh non-idempotent send safe.
- **Reconciliation**: startup plus a one-minute bounded sweep finds ready/retry-due work, expired pre-send leases and unfinished admissions. `sending` after a lost worker becomes unknown and follows adapter reconciliation, not ready. Provider reconciliation itself has a finite attempt/time budget and falls back to human review. pg-boss queue completion acknowledges processing of one wakeup, not external delivery.
- **Permission time**: event admission checks current rule authority and CRM visibility; every delayed database/network action rehydrates its execution actor and intersects CRM authority with current app/grant, connection ownership/delegation, selected resource policy, permitted fields and rule version. An event's actor is provenance, not authority conferred on the rule owner. Store both separately. The intended execution principal comes from ARCH-002/004 and cannot default silently to the administrator who installed a connector.
- **Execution fence**: claim and authorization use current policy/connection/resource generations. Re-read the gate immediately before starting I/O; local block or changed generation prevents a request that has not started. Do not hold DB transactions open across network I/O. A revoke/cancel racing after the final check or after network start may still yield a remote effect; abort is best effort, and the outcome must remain confirmed/unknown as observed. No claim of instantaneous remote recall is made.
- **Pause, remove and cancellation**: disabling a rule stops new admission and invalidates pending unsent effects; connection pause/revocation similarly blocks them. Existing manual workflows retain their documented pause-versus-cancel semantics. Cancelling a run stops subsequent steps, not already committed tasks or sent content. Long-running external steps need their own fenced cancellation and honest in-flight state, not a silent change to current manual-run behavior.
- **Reauthorization/resume**: preserve stable account identity; require explicit selection of held work, current rule/resource/disclosure revalidation and an age bound. Default does not flush a pre-reconnect backlog. Credential replacement alone cannot authorize a previously denied destination or unsafe replay.
- **Replay**: finite preview by cursor/window and explicit operation identity. Default replay fills missing admissions or retries eligible existing intents without creating duplicate effects. A deliberate resend is a separate capability, confirmation and audit event. Unknown outcomes cannot be cleared by generic retry tooling.
- **Loop prevention**: propagate trusted causation IDs and a bounded provenance chain. Initial local policy rejects repeating an `(integration/workflow rule, aggregate, action kind)` within one causal chain and caps the chain at eight automated hops. Later explicit loop/iterator semantics require a reviewed replacement; stripping provenance to bypass the cap is not allowed. Manual edits start a new authenticated root.
- **Privacy and localization**: queue/job/log payloads contain IDs, reason codes and bounded correlation only. Error strings cannot embed provider bodies, tokens, mail/SMS content or hidden record fields. UI and operator messages have FA/DE/EN keys and show permission-denied/unknown/paused distinctly. Channel renderers escape text and validate links; link-only is the Slack default, while other channels require their own disclosure contract.

The retry/lease/hop defaults above are selected local architecture defaults so the implementation has finite behavior to test. They do not assert provider limits, live entitlements or existing implementation. A provider-specific change must be recorded with its contract evidence rather than quietly changing a global guarantee.
