# Period forecast scenarios

The Performance Forecast view runs a read-only native what-if scenario. It uses the period forecast kernel’s factor validators and an open-only read of the existing inventory capture query.

The version 1 adapter requires the authenticated server session and actor, a single explicit currency and pipeline/owner selection, and a bounded fixed civil target. It owns a fresh read-only repeatable-read transaction. Its first data statement captures the native witness and database wall clock. It checks current session and actor authority, restricts the actor to the request ceiling, and rejects a named pipeline, user, team or owner scope it cannot authorize. It resolves the target in the actor's current timezone using normal report boundaries and accepts only an entirely future target at that cut.

The eligible roster is all currently open deals in that exact authorized scope. Native capture must be installed and healthy. Every deal and referenced stage/pipeline must have a matching current capture tip visible at the cut. Missing or conflicting capture and cap overflow withhold the entire scenario result. A fully qualified empty roster is separately available with zero members. There is no fallback to mutable deal IDs as incarnation evidence.

Each named scenario requires explicit eventual-win and conditional in-period close factors, with null representing a missing factor. The optional exact size factor and the two probabilities use PeriodForecast version 1. The same manual assumptions are applied uniformly to the entire scoped roster, with server-stamped evidence, and original recorded values retain exact currency decimals. Recorded expected close dates never create timing probabilities. The output exposes assumption values, resolved target, observed cutoff, exact scenario totals and coverage. It omits raw contributor IDs, roster witnesses and account data. Scenario names identify what-ifs. They do not assert statistical ordering, guaranteed revenue, or calibrated predictions.

The protected POST carries assumptions in the request body and uses the existing CSRF check. Editing input clears the displayed result. The native and browser fixtures cover capture availability, exact arithmetic, unknown factors, record visibility, future targets and the rendered result. Installed capture admission, saved forecast custody, actual settlement and calibration remain separate.
