# Transactional analytics capture — private source proposal

Bounded foundation for [SP-08.2 / #596](https://github.com/KhademOHAli1/warpdrive/issues/596), [SP-08.3 / #597](https://github.com/KhademOHAli1/warpdrive/issues/597) and later movement/snapshot acceptance. This source has not been executed, type-checked, natively tested or admitted as a canonical migration. It does not complete the analytics programme.

The proposal owns [Drizzle metadata](../../src/db/schema/analyticsHistory.ts) and an [unnumbered SQL unit](history-capture-proposal.sql). No schema-index export, numbered migration, historical SQL, journal or generated snapshot is changed. Fetched main `0064808f` ends at canonical `0105_workspace_billing`; the next ordinal must be checked and reserved at admission. The SQL explicitly opens and commits one transaction for a disposable fixture. Canonical integration must let the migration framework own that same boundary, preserving the reviewed inner SQL rather than nesting transaction commands.

## Capture boundary

`AFTER INSERT OR UPDATE OR DELETE` triggers observe actual `deals`, `stages` and `pipelines` rows. This includes raw SQL, bulk updates, imports, stage retirement and valid FK cascades that omit the application change log. The existing board notification remains unchanged. No actor, command, event provenance, historical stage entry or purchase is inferred from a nearby audit row or the current owner.

| Export / table                                            | Contract                                                                                                                                                                                                                                                                    |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `analyticsHistoryCoverage` / `analytics_history_coverage` | Immutable singleton activation ID/version, database observation time, top-level activation XID, baseline MVCC snapshot and physical baseline counts.                                                                                                                        |
| `analyticsHistoryEvents` / `analytics_history_events`     | Shared identity `ordinal` as bigint, unique event UUID, activation/entity/incarnation, baseline/insert/update/delete kind, version, top-level XID, observation timestamp and native observation snapshot, before/after projections and write UUIDs, nullable actor/command. |
| `analyticsHistoryHeads` / `analytics_history_heads`       | Mutable capture-owned `(entityKind,entityId)` head with current physical incarnation, active flag, last captured event ordinal/write UUID and observation bounds. Older incarnations remain in the event table.                                                             |
| `analyticsReportSnapshots` / `analytics_report_snapshots` | Immutable storage capacity for report/model definitions, scope, currency/calendar/zone, target period, cutoff, actual MVCC membership and constituent facts. No application writer or reader is implemented by declaring this table.                                        |

The shared bigint identity gives deterministic raw ordering across all three entity kinds. Drizzle uses `BigInt` mode; server DTOs must serialize ordinals and counts as decimal strings. Aborted transactions and savepoints leave harmless identity gaps.

Deal projections retain title/status, exact text value/currency, owner/pipeline/stage, creation/win/loss/stage-clock dates, expected close date, archive/delete state, person/organization links, source identifiers, visibility fields, loss reason/ID and last/next activity instants. Typed projection functions select these fields directly rather than serializing unrestricted `custom_fields` first. Timestamps use explicit UTC with six fractional digits; expected-close dates use ISO Gregorian formatting. SQL numeric values become text before JSON is stored. Null money remains null.

Stage projections retain name, order, pipeline and rotting days. Pipeline projections retain name, order, visibility group and archive state. Metadata-only board position, `updated_at`, source-row creation timestamps on definitions, and deal write-UUID rotation alone do not emit an event. A changed activity clock or visibility field is material. `heads.lastWriteVersion` means the last captured material event's after token, not necessarily the live row token after ignored UUID rotations; readers must not require those tokens to be equal.

Source primary-key updates fail closed. An explicit delete followed by insert creates a fresh incarnation even when the same UUID is reused. Source-table `TRUNCATE` is rejected because it bypasses row capture, including when empty or reached through `CASCADE`. This restriction needs real fixture/maintenance compatibility review before admission; dropping an entire disposable test database remains the appropriate isolation boundary. There is no runtime bypass GUC or silent backfill path.

## Atomic activation and honest legacy coverage

Installation requires READ COMMITTED and locks the three source tables in `SHARE ROW EXCLUSIVE` mode before any baseline read. Baseline rows, physical heads, count verification and capture/immutability triggers become visible in the same transaction. A failure rolls the entire installation back. A second installation is rejected by existing objects rather than creating another apparent history start.

Every physical source row is baselined, including archived and soft-deleted deals. Capture completeness and report eligibility are distinct. The baseline records what existed at activation; its stored `createdAt`, `stageEnteredAt`, close dates and imported assertions do not prove past transitions. Earlier periods remain legacy/incomplete. Baselines cannot be relabelled as creation events or completed stage stays. Importing a backdated field after activation creates a current observed correction with that asserted value, not a fabricated earlier capture.

`active` on a head means that physical incarnation still exists. It does not mean that a deal is open, unarchived, undeleted or visible. A hard delete closes its physical incarnation; reinsertion replaces the current head with a different incarnation ID. Retained events for the previous incarnation cannot inherit access merely because a new record reused its UUID.

## Observation, transaction folding and definition versions

`observed_at` is a database wall-clock observation during event append. It is not transaction start or commit time. An earlier allocated ordinal can commit later than a larger ordinal. A maximum ordinal or timestamp alone cannot reproduce an earlier reader's known event set.

Each event therefore retains `observation_snapshot` using PostgreSQL 16's native `pg_snapshot`. The top-level `transaction_id` comes from `pg_current_xact_id()`, which also returns the top-level XID from a subtransaction. Definition selection can test other transactions with `pg_visible_in_snapshot(definition_event.transaction_id::xid8, row_event.observation_snapshot)`. This avoids associating a deal with an uncommitted concurrent stage rename merely because that rename has a smaller ordinal. The PostgreSQL documentation explicitly warns against supplying subtransaction IDs to the visibility test. [PostgreSQL 16 transaction and snapshot functions](https://www.postgresql.org/docs/16/functions-info.html#FUNCTIONS-PG-SNAPSHOT).

Raw row-write observations remain original evidence. Published reports separately fold all writes for each `(entityKind,entityId,incarnationId,transactionId)` from first-before to last-after. In-transaction reordering placeholders or an A→B→A write sequence are not separate published configurations or business stage visits. Same-transaction final definition folding must be handled explicitly alongside other-transaction snapshot visibility; a global ordinal comparison is insufficient. A transaction may still contain several genuine commands, so version 1 cannot distinguish their actor/operation identity until a trusted command adapter is qualified.

This first scope omits custom-field/label history, organization-dimension history, leads, contacts, campaign touchpoints, orders, contract/billing and delivery sources. Those remain governed extensions in the programme matrix. Current firmographics or present stage ordering must not be substituted for missing historical versions.

## Immutable report and forecast snapshots

The snapshot table preserves the actual native MVCC snapshot and original per-record facts rather than relying only on an event high-water mark. A late-committing event with a smaller ordinal must remain excluded if its top-level transaction was invisible at capture. `eventHighWaterOrdinal` is only an optional scan bound; membership still requires the stored visibility snapshot or an explicitly preserved constituent set. Stored `pg_snapshot` is serialized visibility information, not an exported live database snapshot or a way to read vacuumed ordinary source-row versions.

A trusted writer must use one consistent database observation for source facts and snapshot metadata, derive the creator from a live authorized actor, pin the report/model definitions and target period, preserve exact monetary facts, and reject pending source events from its own transaction. Own writes are a special MVCC visibility case and cannot be reconstructed using the other-transaction predicate alone. Forecast records must name outcome and timing assumptions; a table declaration supplies no model validation or forecast accuracy.

An internal inventory writer uses the first data read of its own repeatable-read transaction to record the native cut and a database wall-clock observation. Broader snapshot kinds, background storage, actual-source adapters and current-permission readers require separate contracts. Currency/zone JSON consistency, source/model qualification and appropriate fact bounds require those server contracts; the generic JSONB storage checks alone do not establish them. A missing captured historical boundary must remain unavailable rather than be inferred from today's inventory.

## Authority and integrity boundary

Capture leaves `actor_id` and `command_id` null. A future trusted transaction adapter needs actual authenticated-command binding; owner, publisher, imported owner fields and client-set session GUCs are insufficient provenance.

History events reject direct inserts and all updates/deletes/truncates. Heads admit only nested capture writes and reject direct changes, deletes and truncates. Coverage and snapshots reject updates/deletes/truncates. Snapshot inserts require repeatable read, exact native witness equality, a cutoff between transaction start and insert statement start, and no captured source writes already pending in that transaction. Guards are enabled `ALWAYS`; nested depth is at least two so legitimate FK/source-trigger nesting can still capture. Security-definer capture uses a fixed search path and qualified static objects. New table/sequence access and public execution of the capture function are revoked from `PUBLIC`.

This protects normal application operations and accidental direct SQL, not a privileged database owner who can alter functions, triggers, ACLs or schema. Least-privilege deployment grants and nested/direct-helper bypass tests remain qualification work. Snapshot insert guards verify database consistency. Trusted custody still requires an exclusive writer identity that owns each fresh transaction, takes its first data observation without importing a snapshot, and validates current authority and the fact payload. Restrict snapshot INSERT to that writer and keep table ownership and source DML outside its privileges. A shared database owner, an imported or long-held snapshot, and arbitrary payloads cannot establish trusted custody through the trigger alone. Deployment privilege separation remains unqualified.

Every historical summary, drill-down, shared snapshot and export must apply the viewer's current record and pipeline visibility and bind the correct incarnation before aggregation. Snapshot creator authority never transfers to recipients. Raw transaction snapshots remain internal. Archived or hard-deleted records require an explicitly qualified retained-history authority; copying their former owner/visibility is not enough. Without that contract, unavailable/permission-limited removal evidence must stay explicit. No independent disclosure, erasure, retention or installed-storage capability is established here.

## Current stage aging and movement

The internal stage-aging reader observes one bounded set of current authorized live deals in repeatable read. It validates the complete active deal chains and current accessible stage and pipeline identities before folding transaction-final changes. Completed duration, current open age and left-censored lower bounds remain separate. The result describes visits made by this current population, not a historical stage census. Missing or reused definitions, lost visibility and committed inactive intervals withhold the report. Historical labels and a viewer projection remain separate.

The internal movement reader compares two creator-owned inventory cuts with the same stored definition and scope. It proves native ordering, bounds the source at the closing cut, reconstructs both books independently, and rechecks current authority before reconciliation. An omitted key proves neither deletion nor absence. A post-close write does not consume the historical corpus budget. Global membership checks can still affect whether a comparison is available; this reader must remain internal until that signal and retained history are qualified.

## Internal current-deal read boundary

`history/repository.ts` first distinguishes missing capture from invalid/unhealthy installation metadata. It checks the 16 expected `ALWAYS` trigger shapes, then reads one authorized live deal incarnation, current pipeline authority, captured events and an MVCC observation in one SQL statement. A direct internal caller cannot widen reporting owner authority beyond `stats.viewOthers`. The reader rejects its own transaction's pending capture writes, invalid state chains and a captured tip that disagrees with the current material projection; metadata-only write-version rotation is allowed.

An event limit of 5,000 produces explicit partial output rather than a complete-history claim. Raw events, contact/account references and transaction witnesses remain internal; a scoped DTO and report service are still required. Hidden/deleted/archived pipelines deny their associated histories. Any reused pipeline UUID is conservatively denied even for its new incarnation until a precise referenced-incarnation resolver is implemented. This avoids using a new pipeline's permissions to grant older facts.

Catalog health and current projection matching are operational checks. They do not prove uninterrupted capture through privileged DDL/function replacement or an unobserved change-and-reversal gap. Current actor hydration/session freshness, canonical migration admission and installed operational controls need separate qualification. Synthetic constructed-actor tests cannot establish those outcomes.
