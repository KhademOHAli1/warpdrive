# Analytics history activation

The checked-out proposal at `6f1b251d59af2b4b0d376c6d82247b9830e755e9` acquires write-conflicting CRM locks, copies every physical pipeline, stage and deal, and enables live capture in the same commit. Running it from normal Compose startup would create a new personal-data store before installed privileges, lifecycle and recovery are established. Keep this SQL outside the canonical migration journal while those gates remain open.

The rehearsal remains outside the canonical journal. The candidate includes Main through `f9f71a2b` with `0109_gmail_last_checked` as the last canonical migration. Any future migration uses the next contiguous ordinal on the live Main journal.

## Smallest useful admission

First ship source and fail-closed readers through the normal review process. Empty storage is separable from recording. If an independently reviewed migration is needed before active recording, admit the empty objects and ledger guards only. Inert storage can also stay private until an activation release is ready. The adjacent unnumbered SQL shows both phases for disposable rehearsal.

1. `history-storage-dormant.sql` creates private empty tables, indexes and functions, and installs ten ledger guards. It reads no CRM row and installs no trigger on any CRM relation. It uses a catalog-first, temporary-schema-last search path for the security definer, and qualifies application relations and functions. Runtime roles and grants are external dependencies. [PostgreSQL 16 guidance for security-definer functions](https://www.postgresql.org/docs/16/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY)
2. `history-activate-locked.sql` rehearses the authorized operator's later atomic cut. It uses the canonical migration advisory key, then takes the same source locks as the reviewed proposal and exclusively locks the dormant ledger. It verifies empty storage, absence of source capture and the ten expected ledger trigger shapes. Explicit per-source row budgets and session timeouts constrain the rehearsal. It temporarily disables the two write guards needed to fill the private empty ledger, checks per-kind baseline and head counts, reenables both guards and attaches the six source triggers, all within one transaction. Uncommitted changes are invisible to other sessions. Rollback releases the locks and restores preactivation rows and trigger state; gaps in the private ordinal sequence are permitted.
3. After the gates below, admit one capture generation and the current-authorized live-history reads that have qualified independently. Keep snapshot INSERT access, arbitrary historical export, retention-only record access, governed input and saved forecast custody out of that activation's grants and released scope. With a trusted reader grant, the current installation reader checks the empty activation before returning history and reports `capture-metadata-invalid`. Without the grants it can currently raise a DB permission error. The installation reader checks effective SELECT on the three required relations before touching coverage and returns the existing `capture-safety-unavailable` state. This is a capability check for the service role. Viewer authorization remains in each read.

Two delivery paths remain possible. A controlled, later canonical activation migration can run after its production preconditions are met and before that image goes to ordinary startup. A separately approved operator activation mechanism would need its own immutable evidence of the exact SQL, prior canonical prefix, activation ID, actor/authority, gates, result and restore lineage. In that mechanism the canonical journal must describe only the dormant objects and must never be edited to simulate an activation receipt. Select one path before numbering or introducing schema changes. These drafts provide a transaction to rehearse and leave both policy choices open.

Use a fresh disposable session that stops on first SQL failure and rolls back or disconnects immediately. Provide finite nonzero `lock_timeout`, `statement_timeout` and `idle_in_transaction_session_timeout`, and an outer wall-clock cancellation. Set each of `warpdrive.analytics_activation_max_pipelines`, `warpdrive.analytics_activation_max_stages` and `warpdrive.analytics_activation_max_deals` to an independently chosen nonnegative fixture bound before the activation script. The bounds restrict the whole baseline; they do not filter rows or grant authority. Failure after a commit response is lost requires checking the actual singleton and guards before a retry. The activation script rejects an existing or ambiguous activation.

A narrow emergency stop can block capture or reads without representing erasure. Do not copy the lead-link proposal's source-key deletion into this ledger. History has old and new cross-record references, free text, chains and downstream manifests. Deleting matching JSON rows without a hold-aware scope, generation impact assessment and restore fence can both corrupt exactness and miss copies.

## Disposable fixture cut

Reuse the canonical rehearsal's populated prefix helper. Prove dormant storage leaves source rows and prior receipts byte-for-byte intact, all four private tables empty, and normal source writes unaffected. Assert a non-owner without history SELECT gets the explicit safety-unavailable state, and the same role with only the intended reader grants observes empty coverage. Then cover missing/zero timeouts, malformed bounds, row budget exceeded, canonical lock contention, active source transaction, an unexpected source capture trigger, disabled or altered ledger guard, late failure after the temporary guard changes, exact baseline/capture and already-activated rejection. After the failure cases assert no coverage or events, the ten original guards still enabled and no source triggers. After success assert a single coverage row, equal baseline/head/source counts, native witness types and all sixteen ALWAYS guards. Exercise the concurrent writer before and after the activation fence, source I/U/D and rollback, privilege denials and current-authority denial cases. Use a source row that was archived before activation to verify the actual coverage policy. These are fixture definitions to implement and run through the existing qualification process.
