# Private governed source custody proposal

The adjacent unnumbered SQL models transactional custody for version 1 validated analytics inputs. It has no production migration number, application route, database role grants, or qualified producers. Neither storage nor a receipt authorizes a report.

An event stores the validated parsed JSON and its exact canonical UTF-8 text. PostgreSQL checks that the two representations agree and that the SHA-256 digest matches the planner's version and domain prefix. The adapter must use the same canonical encoder as `analyticsInputAdmission.ts`, including its treatment of optional fields and exact string spellings. PostgreSQL JSON output is not that encoder. The payload keeps original money, offset instants including nanoseconds, source calendar, and governance references. The database assigns a separate receipt timestamp and uses bytewise keys for opaque source identifiers. Incoming text must be representable in PostgreSQL JSON and UTF-8 before any write.

One immutable event is stored for each producer/event ID and each producer/source-record/revision. A correction names the immediately previous revision and a different event ID. Its composite foreign key binds the same producer, source record, and event family. Together with the unique revision key, this prevents gaps, forks, and correction into another chain. The SQL checks identity metadata, digest, and correction shape. Full payload, assignment, and entity-link validation remain adapter work.

Each accepted delivery has an immutable receipt for one producer and one verified principal. A line binds its original input index to the event and to the exact configured family grant and policy version. The event links back to its first line through a deferred foreign key. A later line for that event is a retry. A deferred receipt check requires every input index and checks the aggregate canonical payload size before commit. No event or partial receipt is usable before that commit.

## Admission transaction

1. Authenticate a current interactive session or registered service credential at the server boundary. Resolve the exact producer and principal from that authority, require one producer per delivery, and reject payload producer mismatches. Resolve consent, source eligibility, CRM identity, and experiment relationships separately. Carry an opaque server authentication receipt reference and, for an interactive request, the verified user ID. Never store credentials or take the actor from source provenance.
2. In a fresh read-committed transaction, lock the registered producer row before reading the receipt view. Serialize all admissions for that producer with `FOR UPDATE`. Verify enabled registration and lock the applicable family grants in a stable order through commit. Recheck active user/session or service authority under the qualified adapter's freshness rules. The line trigger independently checks the registered producer and exact grant with row locks. It cannot authenticate a principal claim supplied to SQL.
3. Read the complete relevant prior receipt view after acquiring the lock. Fetch every touched source-record chain and each incoming or referenced producer/event key. Deduplicate the combined lookup, enforce the 5,000 receipt cap, and apply the pure admission planner. The producer/event and producer/source-record/revision indexes support these reads. A truncated view is unavailable.
4. Insert the authenticated header, the planned appends in predecessor order, and all lines in original input positions. An exact retry adds a delivery line but no event. Reject conflicting reused keys and stale corrections. Commit, including deferred checks, before returning an acknowledgment. The original event and receipt stay unchanged.

Keep a finite lock and statement timeout. Roll back a failed transaction. A bounded fresh retry on serialization failure or deadlock must reacquire authority and rebuild the plan. An ambiguous commit can replay the same event IDs and exact payloads. It may create another delivery receipt, since `batch_id` is a delivery label, while existing event uniqueness prevents another fact. A uniqueness exception is not evidence of an exact retry. Confirm the committed receipt and fingerprint before reporting a replay.

## Authority, bounds, and lifecycle

- The producer starts disabled. Governance provisions each immutable, versioned principal/family grant. Revoke a grant once and issue a new row for a new authorization. Disable the producer to stop admission across its grants. Re-enabling the same registered producer requires a governance decision about still-valid grants. Never reassign its namespace to another producer.
- No public SQL access is granted. A future narrowly privileged adapter or reviewed database command must own locks and writes. Do not give it control-plane update privileges just to obtain a row lock. Keep producer registration and grant changes under separate governance authority. PostgreSQL ownership or DDL privileges can bypass these controls and remain outside the normal adapter threat boundary.
- Bound the raw delivery before parsing, with at most 500 events, 32 KiB canonical text per event, and 4 MiB canonical text across a receipt. Prior planning reads metadata and fingerprints, not raw payloads. Page any qualified custody audit by stable keys and apply current authority before returning details. Keep the internal authentication reference and raw payload out of report and export DTOs.
- Stored facts are immutable under routine DML. Corrections append new revisions. A grant revocation or source disable stops new admission and must affect reporting under the current source policy. Earlier receipts do not establish present authority. Deleted users do not rewrite actor references in historical receipts. Their pseudonymous IDs and input payloads still require a real retention and erasure policy before production use. This proposal supplies neither an erasure mechanism nor permission to retain revoked sources indefinitely.
- Before migration admission, qualify actual writer and reader roles, source connections, atomic rollback, concurrent retries, revocation races, receipt completeness, and permitted lifecycle handling in the disposable native lane. No SQL, generator, database, or heavy checks were run for this draft.
