# Private forecast custody proposal

This is a disposable version 1 proposal for #600. Apply `forecast-custody-proposal.sql` after the private history capture proposal in a fresh test database. The fixture is intended under `src/features/stats/history` and expects the SQL at `docs/analytics/forecast-custody-proposal.sql`. The proposal introduces no journal ordinal, canonical schema registration, application route, service credential, role or writer grant. Any existing generic forecast rows need a deliberate reconciliation before adoption.

Forecast custody extends the immutable report snapshot row. Its existing native insert guard admits only an exact repeatable-read witness with a valid cutoff and no pending captured source writes. The forecast guard stamps insertion time, verifies an active creator, validates the exact resolved target and its civil date labels, checks each submitted member against the live captured deal tip and its native visibility, and matches all three scenario contributor sets to the submitted open roster. It preserves versioned exact request and payload UTF-8 bytes and stamps separate SHA-256 digests. Inventory rows cannot carry forecast custody fields.

The trusted adapter must authenticate the creator from the server session, intersect the request and current durable authority, resolve owner/team, pipeline, currency and viewer scope, and use a fresh pool-owned read-write repeatable-read transaction. Its first data read must take the native snapshot and sample the database wall clock. The adapter must qualify capture health, all source and referenced stage/pipeline incarnations, live projection equality, and the complete eligible roster under that cut. Native validation confirms submitted member facts. Completeness and authorized population still require the adapter.

Resolve the target through the owning calendar and timezone contract. Freeze the report/outcome/model definitions, original money and exact scenario assumptions at the cutoff. Recompute `calculatePeriodForecast` with every qualified captured row and admitted evidence, and verify its output before encoding. A storage trigger does not validate model authority, evidence vintage, or recompute scenario arithmetic. Use one deterministic versioned canonical encoder, exact string amounts and UTC microseconds. Its request bytes must bind all normalized request intent, explicit assumptions or their immutable model inputs, and the correction link. Do not include newly sampled cutoffs or outcomes in the request key comparison. Its payload bytes must bind those request bytes structurally, the native snapshot, creator, activation, roster and complete result. Database JSONB equality and hashing preserve and bind supplied bytes. They do not prove canonical ordering or reject duplicate JSON keys in raw text.

The adapter may confirm a retry only after fresh authorization for the same principal and scope, exact request-byte comparison and digest verification against an already committed receipt, and validation of its stored payload and custody identity. A duplicate request key or missing connection acknowledgment does not establish an exact retry. A different normalized request with the same key fails. Concurrent uniqueness or repeatable-read failures require a new bounded transaction and fresh authority. Commit and independently verify the receipt before acknowledging it.

A correction is a new prediction with a fresh cut and request key in the same creator, scope, currency, report definition, activation and target. It must point to an earlier committed matching forecast and provide a reason. One successor per snapshot prevents forks. The model definition can change on the successor. The earlier row, witness and bytes stay immutable. Use the explicitly selected original for evaluation, and identify later versions as separate predictions. Post-target retrospective correction or annotation, retained-record access and published-series policy are separate work.

The insertion timestamp is a database observation before target start. It is not a commit timestamp. The future writer must record independent native visibility of the committed receipt before target start to qualify it for strict retrospective evaluation. A transaction that commits late cannot supply that proof from insertion time. Settled actual collection, restatement policy and probability qualification remain separate.

The future reader must reauthorize every saved member and definition against current viewer and pipeline authority, reject unavailable incarnations, verify digests and supported versions, and keep native witnesses, audit IDs and private bytes internal. Replaying a shared definition cannot transfer creator authority. Least-privilege deployment must separately qualify exclusive fresh writer custody, typed helper execution, required read/row-lock privileges and no source or table ownership. Catalog health must cover the forecast trigger and both unique indexes in addition to base history health. The disposable fixture uses its own database owner and synthetic assumptions. No native execution or acceptance is recorded.
