# Governed analytics inputs

`analyticsInputContracts.ts` provides executable version-1 payload contracts for producers and future authenticated adapters. This is a bounded prerequisite for [#595](https://github.com/KhademOHAli1/warpdrive/issues/595), [#636](https://github.com/KhademOHAli1/warpdrive/issues/636), [#604](https://github.com/KhademOHAli1/warpdrive/issues/604) and the full programme's source requirements. It supplies validation only. Ingestion, persistent idempotency/correction receipts, source authentication, permissions, source connections and real-data qualification remain required implementation.

Adapters can call `analyticsInputBatch.safeParse(payload)` to obtain typed events or structured validation issues. Batches are bounded to 500 events. Every event declares a producer, producer-local source-record/event ID, revision, capture/effective instants, source calendar, timezone and Gregorian ISO storage. IDs stay distinct for persons, accounts, opportunities and purchases. These fields describe source evidence; they confer no CRM visibility, mutation or identity-link authority.

| Family                         | Required meaning                                                                                                                                                       |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Touchpoint                     | Recorded or unresolved identity; captured/direct/unknown/uncaptured source; channel, optional campaign and interaction type.                                           |
| Campaign cost                  | Channel/campaign, observation window, original money and media/fully-loaded/other basis.                                                                               |
| Commerce                       | Order, purchase or refund; original order ID, purchase identity for purchase/refund, quantity/unit and original money. Refund direction is explicit in the event type. |
| Billing                        | Contract start/end, invoice, payment or credit; contract/identity, recurring/one-time basis, coverage window and original money.                                       |
| Delivery cost                  | Service, cost basis, hours/units, observation window and original money.                                                                                               |
| Experiment assignment/exposure | Experiment, variant, person/account/geo unit and assignment method or recorded assignment-event reference.                                                             |
| Geographic outcome             | Geo/window, distinct people/account denominator, exposed/converted counts and optional monetary outcome. Control conversions can exist with no treatment exposure.     |
| Customer signal                | Recorded survey/ticket category, state and separate source identities, with optional governance references in provenance.                                              |

Money uses the existing supported currency set and exact nonnegative major-unit decimal strings within numeric(18,4) capacity. A JSON floating-point amount, unsupported currency, absent unit or implicit toman conversion fails validation. Civil-day windows retain ISO dates; instant windows require explicit offsets. Exclusive ends must follow starts, including sub-millisecond instant comparisons. Counts are bounded nonnegative integers; geographic observed units cannot exceed eligible units.

Within a batch, producer/event keys and producer/source-record/revision keys are unique. Corrections name a different earlier event/revision and a nonblank reason. When that target is in the batch, its source record, producer, family and revision must match. Original and correction payloads remain separate.

`analyticsInputAdmission.ts` plans an entire parsed batch against a bounded, complete set of prior receipt facts. Stable canonical JSON and domain-versioned SHA-256 distinguish an exact retry from changed payloads reusing an event or revision key. A new correction must advance one revision from the same producer, source record and family and point to the current tip. Input order does not select a correction winner. A conflict rejects the entire batch, with no appends or implied approvals. The planned append is not a durable write.

The database adapter must prove receipt completeness, authenticate the producer and actor, verify exact entity relationships and assignment/exposure links, and check and reserve both keys under one transaction. Separate source custody, privacy lifecycle and the proof of real-data eligibility are still required. A parsed payload or an admission plan does not qualify a fact, recurring revenue, causal estimate or viewer disclosure.

MMM, attribution, lifecycle economics, experiments and predictive analyses remain included programme work. Their implementations must consume qualified source adapters and retain their model/eligibility assumptions. These schemas do not supply invented source observations, advertising actions or financial writes.
