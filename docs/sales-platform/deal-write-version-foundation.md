# Database-owned deal revision foundation

This increment contributes to technical issue #906. It adds revision storage and ownership for later deal commands. It does not complete the deal journey in #82, installed migration lineage in #533, or the writer-admission programme in #589.

`deals.write_version` is a non-null UUID. PostgreSQL assigns a fresh opaque value on every ordinary `INSERT` and `UPDATE`, including copied or explicitly supplied values, SQL no-ops, and derived-date updates that preserve `updated_at`. An explicit update cannot restore an older token. UUID parsing and the column's non-null constraint remain independently enforced.

Canonical `0099_deal_write_version` preserves the reviewed private `0101` SQL body exactly. It adds the column without a volatile default, backfills existing rows, then sets the default and non-null constraint before installing the ownership trigger. Backfill preserves every old deal field, including PostgreSQL timestamp precision and row identities. The generated Drizzle snapshot describes the added column; the custom SQL retains the backfill and trigger that automatic column generation alone would omit. All canonical `0000` through `0098` SQL and prior journal entries remain unchanged.

The backfill updates every existing row and emits WAL. The migration holds the table's exclusive lock and performs the non-null scan within the existing canonical migration timeouts. It is not an online migration without locks. Large installed tables need measured upgrade planning, and unknown private installation histories remain subject to the existing fail-closed lineage admission.

The new field is ordinary non-secret row metadata. Full-row ORM reads can carry it. No command requires or consumes it yet: the current timestamp comparisons, input contracts, narrow acknowledgements, client caches and automatic-writer admission remain in place. This storage increment therefore does not solve the existing timestamp-CAS races or establish the later authority and retry contracts.

The follow-on command work must use current authority, preserve hidden linked-contact masking, return an authorized fresh snapshot or narrow acknowledgement followed by reread, and adopt the opaque revision coherently across its selected transports. Creation also needs a durable operation receipt for uncertain-response recovery. No archived Sales DTO, client, authority helper or temporary migration overlay is activated here.
