# Native deal creation and uncertain responses

The board and per-stage Add Deal form use a versioned native command. A submitted deal keeps the same actor-bound operation and normalized intent if the acknowledgement is lost. The backend commits its completed receipt with the deal, labels and transactional board event. Matching retries read the original current authorized result. MCP/import keep their separate shared domain API. The retired unkeyed native action rejects requests before context or effects, after its CSRF check.

Receipts contain account ID, random operation ID, immutable fingerprint version and hash, nullable deal ID, and database receipt time. No raw title, contact details, custom values, session or credential is stored. These are pseudonymous provenance records, not anonymous data. Hard deletion nulls the deal link and retains the completed tombstone. Actor deletion is restricted pending its separate erasure/lifecycle policy. No routine receipt expiry is admitted while an actor can retry. Privacy discovery explicitly classifies this store as `unsupported`, with `candidate_links_only` scope; no complete subject-disclosure or erasure adapter is claimed.

The authenticated server layout supplies public actor identity. A keyed provider and synchronous unmount guard isolate late callbacks. The server independently authenticates the request and requires the expected account to match. Retained drafts live in account-partitioned memory for this JavaScript document: modal dismissal/client navigation preserve unresolved intent; full reload is warned about and never silently retried. This does not repair every application cache/account transition.

One document-wide attempt owner per account covers preparation, contacts, dispatch and read reconciliation across modal instances. Ownership releases by exact token even after unmount. Known-created state cannot regress; after an uncertain outcome, later negative responses retain the original identity because an old backend request may still finish. Only an initial definitive rejection without prior uncertainty releases its identity. Deployments must retire old unkeyed native-action servers before claiming this new native command contract across the running application.

An uncertain save retries the same frozen request. A known saved deal whose current view failed retries only the authorized read and board refresh. The narrow acknowledgement has ID, update time and database-owned revision. Board/list queries return revisions with their actual masked fields; no token is grafted onto an old optimistic row.

Known-created recovery uses a separate read-only receipt-backed current-ID acknowledgement, including current pipeline visibility and post-lock linkage checks. It does not infer hidden status from absence in the original pipeline's open board. A visible won or moved deal remains recoverable. Read/authorization/conflict failures preserve known creation and its key; an authorized unavailable result never creates again.

Inline organization/person creation is separate and has no durable receipt. Deal-specific proxies check the expected account before delegating unchanged contact permission/validation behavior. Acknowledged contact IDs are preserved before the next request. Unknown contact responses require explicit selection/reconciliation and are never automatically resubmitted. Existing/null contacts are the first journey selected for qualification. A complete duplicate-safe inline-contact journey is not claimed.

Creation uses outer READ COMMITTED and the participating authority fence, current routine session/actor checks after waits, and a PostgreSQL wall-clock checkpoint after local effects/result reads. Supported legacy routine sessions remain compatible. Operator/direct SQL and unenrolled writers remain outside the guarantee; time is not frozen during COMMIT or response delivery.

An operation advisory lock precedes a plain receipt lookup. Replay locks pipeline then deal and rechecks linkage; a receipt row is never locked before its deal, avoiding inversion with the hard-delete FK. New creation protects selected pipeline/stage, definitions/settings and owner/contact references. Post-effect denial forces outer rollback. Driver/commit failures remain uncertain. No external provider I/O occurs inside this callback.

Qualification is tracked on #906. The real predecessor HTTP reproduction observed one committed deal before response loss, then two after unchanged-form retry. That failure remains preserved; it is not a modified-application browser success.
