# Product-signal source decision

Research date: 31 October 2026, Europe/Berlin. Scope: SP-12.1 design/research, with UX-16, UX-08 and UX-19 implications. Ali authorized research and judgment to select a suitable implementation default. This decision does not assert access to customer telemetry or qualify a live source.

## Decision

Use a **customer-controlled first-party event API** as the default source contract. Choose **Warpdrive itself, running locally with synthetic accounts and records**, as the reference product for examples, dry runs and later runtime qualification. Offer PostHog mapping and Segment-style event import as optional adapters to the same contract. Neither service is a required infrastructure dependency.

Position the feature as explainable account-level product signals that help sellers decide what to review. Show demonstrated value, fit, explicit intent and missing evidence separately. Avoid a universal lead score or a claim that clicks predict purchases. These are product/design judgments based on the comparisons below, not measured customer outcomes.

The named reference product is a development choice. No source instance, external account, operational data owner, retention agreement or permitted live feed has been qualified by this research. No SDK, dependency, credential, provider setting or application code was changed.

## Why the installed PostHog SDK is not the source decision

The selected repository already declares `posthog-js` and `posthog-node` in `package.json`. `src/features/observability/TelemetryProvider.tsx` enables configured UI/performance telemetry; `capture.ts` identifies the signed-in internal user and sends scrubbed custom events. The inspected `events.ts` includes modal, error and board-drag events.

Those source facts do not establish an approved customer product-usage feed, account mapping, runtime credentials or delivery guarantees. Preserve that observability system. Do not silently reuse its project token, employee identity, autocapture, replay or historical events for sales qualification. Product signals need a separately declared purpose/source contract even when an optional adapter uses the same provider technology.

PostHog's official documentation distinguishes custom event capture from automatic page/click capture. That supports using deliberate product events for this feature rather than treating ambient browser telemetry as value evidence. [PostHog capture documentation](https://posthog.com/docs/product-analytics/capture-events).

## Reference product and meaningful signals

Use an isolated synthetic Warpdrive product account, representing a customer deployment, and synthetic product users. Map that account explicitly to a synthetic CRM customer organization. The product account is not the destination authentication workspace; a product user is not automatically a CRM contact. No real self-hosted installation should report usage merely because this reference exists.

Proposed event names below are original design hypotheses. They are not claims that this instrumentation already exists. Emit completion events from successful domain operations after commit, not from button clicks. Reuse stable command/event boundaries when implemented.

| Dimension          | Proposed evidence                                                                             | Interpretation and exclusion                                                                                                                             |
| ------------------ | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Setup              | `pipeline.created` with only approved structural properties                                   | Useful onboarding context, insufficient activation by itself. Exclude demo seed/import history unless explicitly marked and included.                    |
| Activation         | `opportunity.created` followed by `follow_up.completed` for that product account              | Candidate first completed sales-work loop. Do not equate a page visit or an opened modal with the loop.                                                  |
| Demonstrated value | The work loop recurs on separate days with successful saved outcomes                          | Candidate repeated use. Explain the event count/window and missing events; an outage is unknown, not disengagement.                                      |
| Collaboration      | `account.user_added` plus successful work by a second identified product user                 | A sent invitation alone does not prove team adoption. No email addresses or CRM record content are needed.                                               |
| Explicit intent    | `sales_assistance.requested` from an actual submitted request, if the product later offers it | Stronger declared intent than visiting a pricing page. Do not invent a billing plan, upgrade request or commercial feature that Warpdrive does not have. |
| Fit                | Source-owner-approved account attributes, such as a declared team-size band                   | Unknown remains unknown. Do not infer fit from employee names, phone country, locale or a guessed company domain.                                        |
| Diagnostic only    | Page views, login, modal open, drag start/cancel and errors                                   | Show separately if useful for source health. Give no default qualification weight.                                                                       |

A reference rule can explain a completed loop and repeated use in a declared window, plus independent fit/intent states. Thresholds are versioned hypotheses for review. They are not conversion probabilities, native user research or evidence of causal sales lift.

## Default contract and adapter boundaries

This is a proposed contract outline, subject to SP-12.2 and the existing SP-06 identity design:

- Required event fields: stable source event ID, schema version, allowlisted event name, source account ID, event time with offset, and bounded allowlisted properties. Actor ID may be absent for genuine account-level events; absence must not manufacture an anonymous contact.
- Server-owned fields: destination workspace context, registered source identity, receive time, authorization and processing status. Never trust a submitted workspace ID as authority. Keep event time and receive time separate and flag skew/late arrivals.
- Stable identity: explicit source-account-to-CRM-company mapping and, when needed, source-user-to-person mapping. Unknown/conflicting identities enter review/quarantine. Email/phone similarity must not merge records automatically.
- Replay: deduplicate by destination/source/event identity; reuse the ID across delivery retries. Keep original event time. Do not turn old imports, replays or a changed threshold into new outreach.
- Data boundary: no raw names, message bodies, contact lists, replay recordings or arbitrary property bags by default. Record a finite source-specific retention policy, suppression/deletion handling and minimal replay tombstones consistent with the owning privacy contract.
- Adapters: map Segment `messageId`, event name, user ID, explicit account context and timestamp deliberately. Segment documents distinct timestamp roles and client clock-skew concerns; preserve provenance instead of treating receive order as business order. See [common fields](https://www.twilio.com/docs/segment/connections/spec/common). PostHog mapping likewise requires an explicit event/account contract and stable identity, not loose matching of person properties.
- No compatibility shortcut: transport authentication, payload limits, deduplication and source deletion must be tested on the actual adapter. Vendor documentation limits do not automatically become Warpdrive limits.

Use the existing shared workflow/communication path only after explicit follow-up activation and permission checks. A product signal is evidence for review; collection permission, CRM access and outreach permission remain distinct.

## Source onboarding UX

Keep the current SettingsCard/Dialog/Select adapters and progressive disclosure. The seller should see the source's meaning and status, while integration diagnostics remain in settings or a details affordance.

1. **Choose how to start:** primary path, First-party events; secondary path, Try a synthetic Warpdrive example. Label the example as synthetic throughout. PostHog and Segment options disclose unavailable/unqualified capability rather than implying a working connection.
2. **Describe the product and purpose:** product/source name, environment, named operational owner and intended sales-review use. Explain which events are collected and which are excluded. A missing owner leaves the source in draft.
3. **Map accounts and optional people:** preview a few permitted synthetic examples; distinguish product account, CRM company and destination workspace. Unknown or conflicting mappings need review, with no automatic merge.
4. **Choose event contract and retention:** show a small allowlist, event/receive-time examples, schema version, finite retention, deletion/suppression behavior and a human-readable rule preview. Do not expose a universal arbitrary-code builder.
5. **Test without sales effects:** validate bounded synthetic events, show accepted/duplicate/rejected/quarantined/late statuses and source freshness. Explain transport acceptance separately from qualification. No messages, deal creation or historical backfill effects follow from this test.
6. **Review and enable:** show source/environment/owner, mapped scope, data purpose, rule version, retention and disabled follow-up summary. Real source activation waits for the declared evidence gate. Follow-up is a separate explicit action.
7. **Operate and recover:** show last successful receive, source outage/paused/degraded states, pending identity review and safe retry eligibility. Pause, revoke, deletion and replay controls must not resurrect removed data or create repeated work.
