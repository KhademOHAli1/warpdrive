# Database qualification runner

The correction sources are prepared and **unexecuted**. No test, lint, typecheck, formatter, database or container run has verified these changes. In particular, the watchdog, abort, late-start supervision and cleanup behavior remain unproved until the actual destructive cases pass. Resume only in the coordinator's finite database window after its disk-space gate. No provider accounts, main/demo databases, host PostgreSQL tools or client installation are used.

Run the dedicated lane from the repository root:

```sh
bun --bun vitest run --config src/db/mailMigrationQualification.vitest.config.ts
```

That config omits the normal global setup and runs one file with one worker. Four functional cases share one disposable PostgreSQL16 container. After it closes, two destructive safety cases each create and remove a fresh container, sequentially. This lane therefore uses three containers in total, with at most one qualification container live at a time. The file directly imports `mailMigrationQualification.test-helpers.ts`, so the existing classifier puts it in the integration lane. The normal full integration command can also start its shared template container. Do not describe the default integration command as one-container execution. Run this dedicated lane separately and exclude it from other selected integration suites. No global classifier/config changes are required. The public same-runtime cleanup API requires the direct `testcontainers` dev dependency, pinned to the version used by `@testcontainers/postgresql`.

The four required functional cases are clean installation, exact baseline82 upgrade, platform84 upgrade, and actual90 locators upgraded through91. Baselines82 and84 include a custom-format `pg_dump` and restore into fresh empty databases using the matching version16 binaries inside the owned container. The90 case captures existing locator UUIDs, UIDVALIDITY, flags, active state and relationships before upgrading, requires unknown historical hashes to remain null, verifies the account/hash index is nonunique and includes inactive observations, then writes repeated aliases and reruns the migrator. Migration91 and its snapshot are mandatory inputs. The runner fails before container creation when91 is absent; alias qualification is never silently skipped. Historical SQL/journal hashes are embedded in `mailMigrationQualificationBaseline.ts`, so shallow Git history does not waive the baseline check.

The actual journal supplies the target, which must include91. The loader captures all SQL bytes, the journal, snapshots82/91 and every per-SQL SHA256 into an owned temporary target and writes an input manifest. Every migration call rechecks that owned target against its captured digests; it never reopens repository SQL as migration input. Restore evidence emits the complete per-SQL manifest, target entry, source commit, migration dirt flag, server/dump/restore versions, archive digest, guard digest and table counts. Qualification of dirty SQL covers those captured bytes; it is not immutable release qualification. Output contains non-secret metadata and hashes. Fixture comparisons cannot print credentials, ciphertext, password hashes or message bodies.

Fixtures cover original Gmail/native-auth UUIDs, original-column values, relationships, encrypted Gmail and schema-valid IMAP/SMTP credential recovery, wrong-key rejection, password verification, valid Base32 MFA-secret recovery, hash-only recovery codes, password/MFA/revoked sessions with production session hashing, Farsi/German preferences, private/shared visibility, archive/trash visibility, both legacy owners' default senders, generation/version fields, exact-source aliases, durable accepted/partial/unknown receipts, attachment metadata and workflow versions/runs/steps. Internal-ID session liveness checks do not present row IDs as bearer credentials or touch session timestamps. Real permission reads and cross-account FK rejections run before and after restore. Historical constraint/index/trigger/function definitions are captured before upgrade and compared afterward. Only the intentional mailbox-owner uniqueness replacement is allowed to disappear. SQL-only workflow publish/version FKs and the immutable-version trigger are also inspected and exercised, rather than inferred from Drizzle snapshots.

Each destructive case holds an actual ACCESS EXCLUSIVE table lock, starts a real `pg_dump`, and requires observing that process blocked on the same relation through `pg_stat_activity` and `pg_locks`. One case waits for the archive watchdog; the other aborts only after observing the wait. A constructed argument list or a rejected command is insufficient. Each case requires the expected timeout/AbortError, exact owned-container absence on the same runtime, and failed database access before releasing the lock. The ordinary dump also uses a 5-second lock-wait timeout. `PGOPTIONS` is not treated as an archive-process deadline.

The source supplies a 45-second SDK startup-readiness limit and a 60-second outer startup deadline. Public lifecycle hooks supervise creation after cancellation, and both success and failure continuations retain cleanup. Migration batches have a 120-second outer deadline; archive commands have a 60-second default deadline. Deadline/abort cleanup removes only the generated owned container name or recorded ID through Testcontainers' resolved runtime, never an unrelated Docker CLI context or a daemon-wide prune. Teardown bounds pool draining, stops the owned container, and removes only its `mkdtemp` tree through nested finalizers. Cleanup needs positive exact-container absence proof; an unreachable runtime is a qualification failure. Individual PostgreSQL queries have 30-second driver/server ceilings and check signals before/after; they do not claim immediate in-flight query cancellation. These are source designs, not runtime evidence.

All databases and archive files belong to the disposable fixtures. Archive passwords are passed through the container exec environment rather than command arguments. Private object bytes, external encryption-key custody, cluster-global roles and real provider behavior remain separate operator qualification gates. This database test does not establish MinIO object restore or external-mail delivery.
